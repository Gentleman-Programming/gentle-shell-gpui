# Integrations

How Gentle Shell GPUI connects to Gentle Shell (the `gentle-shell --mode rpc` backend of each agent tab) and to external services: which process it launches, which protocol it speaks, which files it reads or writes, and who owns them. At the end, how to add a new integration without breaking the boundaries in [`architecture.md`](architecture.md).

## Launcher: `crates/pi-rpc/src/launch.rs`

### `resolve_backend(cwd) -> LaunchSpec`

Program lookup order:

1. `GENTLE_SHELL_BIN`, if not empty.
2. `bundled_launcher()`: Gentle Shell installed in its own folder, the self-contained install (4.7, the one created by its installer and by `gentle-shell upgrade`) or, on Windows, gentle-ai's managed install. It wins over a global npm `gentle-pi` left on the PATH.
3. `gentle-shell` on the combined PATH (`which::which_in` with `search_path()`).

If nothing is found, the error asks for `npm i -g gentle-pi` or `GENTLE_SHELL_BIN`. Whichever launcher is found, `launch_spec` checks whether it belongs to gentle-ai's managed install (see below) and then starts that install's Node instead.

`LaunchSpec { program, args, cwd, env, launcher, bundled }`:

| Field | Value |
| --- | --- |
| `args` | `GENTLE_SHELL_ARGS` split by `split_args()` (spaces separate; `"…"`/`'…'` keep spaces; backslashes literal), then `--mode rpc`, then `--append-system-prompt <file>` (`set_system_prompt`) and `--extension <file>` for each of `set_extensions` (the generative UI extension). Managed install: its `gentle-shell.mjs` instead of `GENTLE_SHELL_ARGS`. An agent tab whose Gentle Shell takes host tools leaves the last two out (see [Host tools in a tab on this computer](#host-tools-in-a-tab-on-this-computer)). |
| `env` | `GENTLE_SHELL_INTERACTIVE_HOST=1` (enables `ask_user_question` dialogs and live helper activity) and `PATH` = combined PATH. Managed install: also its own environment (see below). An agent tab adds its own variables (`backend::launch_spec`): the Agent UI mode, the canvas file, and `GENTLE_DESIGN_OPEN_BROWSER=0` whenever the app opens the design canvas itself (see Design canvas). |
| `cwd` | The tab's folder |
| `launcher` | The `gentle-shell` command a person runs: what Settings shows and messages name. `program`, except for the managed install (its `bin\gentle-shell.cmd`). |
| `bundled` | `BundledInstall { node, package, managed }` of a complete self-contained or managed install; `None` for npm/pnpm/yarn **and for an incomplete install** (see [The `gentle-pi` and Pi packages](#the-gentle-pi-and-pi-packages)). `managed_by_gentle_ai()` reads `managed`. |

Launcher subcommands go through `spec.launcher_command(sub)`: the same program, the arguments before `--mode`, then `sub`, in `cwd` with `env`. Used by `--version` (`run_version`), `upgrade` (`settings/upgrade.rs`, `setup/gentle.rs`), `install`/`remove` (`setup::run_gentle_shell`), `setup` (`setup/gentle.rs`), `mcp` (`setup/maestro.rs`) and the commit message (`files/changes.rs`, `--print`).

### Self-contained install

`bundled_candidates` defines where the launcher is looked up:

| OS | Launcher |
| --- | --- |
| macOS and Linux | `~/.gentle-shell/bin/gentle-shell` |
| Windows | `%LOCALAPPDATA%\gentle-shell\bin\gentle-shell.cmd`, then `%USERPROFILE%\.gentle-shell-bundle\bin\gentle-shell.cmd`, then gentle-ai's managed install, `%LOCALAPPDATA%\gentle-shell\install\bin\gentle-shell.cmd` |

`bundled_install(launcher) -> Option<BundledInstall { node, package, managed: false }>` recognizes the generated script by the `BUNDLED_LAUNCHER_MARK` marker (`"gentle-shell bundled launcher (generated; do not edit)"`) and derives the layout:

```text
<prefix>/
├── bin/gentle-shell[.cmd]        # generated script
├── runtime/node-<v>/bin/node     # or node.exe on Windows
├── current                       # link to the active version; on Windows, a file with the folder name
├── versions/<v>/node_modules/gentle-pi
└── config/gentle-ai              # config folder (see Homes)
```

`resolve_backend` stores it in `spec.bundled`, which `gentle_pi_root` and `pi_package` (see [The `gentle-pi` and Pi packages](#the-gentle-pi-and-pi-packages)), `version_output` and `LoginHelper::spawn` (to use the install's own Node) read.

### gentle-ai's managed install (Windows)

The `gentle-ai` TUI installs Gentle Shell on Windows as one folder (its "Separate" install, gentle-ai `internal/shellinstaller`), always `%LOCALAPPDATA%\gentle-shell\install`:

```text
<root>/
├── bin/gentle-shell.cmd     # "<root>\supervisor.exe" shell launch "<root>" gentle-shell %*
├── supervisor.exe           # gentle-ai's launcher: checks the folder, then starts Node
├── manifest.json, selection.json, main.json (Main channel only)
├── runtime/node/node.exe    # its Node (runtime/go, runtime/codegraph beside it)
├── prefix/node_modules/gentle-pi/bin/gentle-shell.mjs
├── agent/                   # Pi's agent dir (GENTLE_SHELL_HOME, PI_CODING_AGENT_DIR)
├── config/                  # Gentle AI config (GENTLE_PI_CONFIG_HOME) and gentle-shell.json (GENTLE_SHELL_CONFIG)
└── home/, state/, tmp/      # HOME/USERPROFILE, LOCALAPPDATA, TEMP of its processes
```

It also publishes `%LOCALAPPDATA%\Microsoft\WindowsApps\gentle-shell.cmd` (on the PATH), a shim that only does `call "<root>\bin\gentle-shell.cmd" %*`.

`managed_install(launcher)` recognizes the binding or that shim (`shim_target`, `supervisor_root`: pure parsers of the two `.cmd` files) and requires `supervisor.exe`, `manifest.json`, the Node and `gentle-shell.mjs` in the folder. The app does not launch through the supervisor: it builds its environment from scratch (`userWindowsLaunchEnvironment`), so `GENTLE_SHELL_INTERACTIVE_HOST` and the app's PATH would never reach Gentle Shell (no Gentle Desktop), and it forwards everything after `--` to Pi, so `--version`, `setup` or `upgrade` would not reach the launcher. Instead `program` is `runtime\node\node.exe`, `args` start with `gentle-shell.mjs`, and `ManagedInstall::env` mirrors gentle-ai's `userWindowsEnvironment(root)`: `HOME`/`USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `TEMP`/`TMP`, `GENTLE_PI_CONFIG_HOME`, `PI_CODING_AGENT_DIR`, `GENTLE_PI_AGENT_HOME`, `GENTLE_SHELL_HOME`, `GENTLE_SHELL_CONFIG`, `GENTLE_PI_NO_SKILL_REGISTRY`, the Go and npm variables, `NODE_USE_SYSTEM_CA`, and `PATH` = its `runtime\node`, `runtime\go\bin`, `runtime\codegraph\bin`, then the combined PATH. The rest of the app's environment is inherited. Not reproduced: the supervisor's integrity check, its Job Object and its shared-Engram decision (Gentle Shell's own Engram handling applies, as with any other install).

gentle-ai is what updates and repairs this install, so for it (`managed_by_gentle_ai`): Setup & requirements turns the Gentle Shell and Companion setup fixes into "Open terminal" with `gentle-ai` (a launcher without a version shows its own error there too). An incomplete managed install, not recognized as one, gets Retry with the refusal and diagnostics described below. It reports Node.js and Go as provided by the install, and Settings offers no `gentle-shell upgrade` (nor writes the update check into its `config\gentle-shell.json`, which gentle-ai verifies). Gentle AI itself is the package-local `gentle-pi\.gentle-ai\v<pin>\gentle-ai.exe`; the Companion setup check reads its pin from that package and the provisioning marker from `config\gentle-shell.json`.

### Combined PATH

| Function | What it does |
| --- | --- |
| `login_path()` | The PATH a session started now would get. Unix: `login_shell_path()` runs `$SHELL -l -i -c "printf '__GENTLE_PATH_START__%s__GENTLE_PATH_END__' \"$PATH\""` with a 5 s limit; the markers isolate the value from whatever the rc files print (nvm, fnm, mise). Windows: `registry_path()` reads the machine's and then the user's saved `Path` with `reg query` (5 s each, `reg_value`) and expands their `%VARIABLES%` (`expand_vars`), so a folder an installer added after the app (or what launched it) started is found. |
| `base_path()` | Login PATH first, then the inherited one, then `go_bin_dir()` (`GOBIN`, else the first `GOPATH` entry's `bin`, else `~/go/bin`; where `go install` puts `gentle-ai` or `engram`) when it exists, without duplicates. Computed once (`BASE_PATH`). |
| `set_extra_path(dirs)` | Folders that go before everything else. `setup::apply_toolchain_path` puts the toolchains installed by the app here (`<data dir>/gentle-shell-gpui/toolchain/{node,npm-global,bin,maestro/bin,music/bin}` and the Java runtime's `bin`), plus the Android SDK's `emulator` and `platform-tools` when an SDK is installed (`devices::android_tool_dirs`: Android Studio doesn't put them on the PATH, so an agent asked to start an emulator wouldn't find them). |
| `search_path()` / `child_path()` | Extra + base. This is the PATH every child receives. |
| `find_program(name)`, `resolve_node(cwd)` | Lookup on that PATH (`which`, with `PATHEXT` on Windows: `.exe`, `.cmd`, …). |
| `forget_cached()` | Forgets the login PATH and the cached `--version` outputs; call it after installing something. |

### Backend version

`version_output(spec)` runs `<launcher> --version` (`launcher_command`) and caches it per launcher, invalidating when the `Stamp` of the launcher file (for a self-contained or managed install, its `gentle-pi`'s `package.json`) or of the launcher config (`launcher_config_path`) changes. `backend_version` extracts the `gentle-shell X.Y.Z` line. `forget_versions()` is used after `gentle-shell upgrade`. If Setup finds no launcher version, `version_stderr` repeats the probe with a deadline and bounded stderr; its first meaningful line is shown with the launcher path. Only an empty stderr uses the old Node/Pi guess. Working launchers keep the original stdout cache and do not run this diagnostic probe.

### `pi_rpc::command`

On Windows it adds `CREATE_NO_WINDOW` (`0x0800_0000`): without it, every console child (git, node, shells, the backend) would open its own window in a release build, and in debug it would attach to the terminal that launched the app. On other platforms it is `Command::new`.

### Where agents run (`gentle_core::backend`, `features/backend/`, `pi_rpc::remote_backend`, `pi_rpc::serve`)

Agents, terminals, git and Setup can run on this computer (the default), in a WSL2 distro, or in any environment a command reaches (a Linux VM through OrbStack or Lima, a container); agents, terminals, files and git can also run on a Gentle Shell server (`gentle-shell serve`, below; Setup only checks it). The choice is the app's `settings.json` key `backend`: absent or `null` for this computer, `{"kind": "wsl", "distro": "Ubuntu"}`, `{"kind": "command", "prefix": ["orb", "-m", "dev", "--"]}`, or `{"kind": "server", "url": "http://127.0.0.1:8787", "device": "dev_…", "name": "pc"}`. Configuration → General → Where agents run sets it. On Windows it lists `wsl.exe --list --verbose` (`WSL_UTF8=1`; UTF-16 is decoded too) and suggests the default distro that has `gentle-shell`. A folder under `\\wsl.localhost\<distro>\` (or `\\wsl$\<distro>\`) runs in that distro whatever is saved (`backend::for_tab`), as VS Code does. An agent tab keeps the backend it first started on, so a restart resumes its conversation there.

- **Agent launch.** `Backend::launch(folder)` is the argv that runs a program in the project folder: `wsl.exe -d <distro> --cd <folder> --exec` (`--exec` passes the arguments without a shell re-reading them), or `<prefix> sh -c 'cd "$1" && shift && exec "$@"' sh <folder>`. `pi_rpc::remote_backend` appends `env GENTLE_SHELL_INTERACTIVE_HOST=1 PATH=<login PATH> <tab variables> gentle-shell --mode rpc` and the app's `--append-system-prompt` and `--extension` files. The tab variables are the same ones a local tab gets (`GENTLE_DESIGN_OPEN_BROWSER=0` among them), so the design canvas keeps the system browser closed in every backend. Variables travel as `env` arguments because `wsl.exe` doesn't forward the host's environment. The host's launcher, `GENTLE_SHELL_ARGS` and PATH stay out. Closing the tab closes Pi's stdin, and Pi exits inside the backend.
- **App files.** The instructions and extensions the app gives every agent are copied into the backend (`~/.cache/gentle-shell-gpui/<content hash>-<name>`, once per content), since a container may not see this computer's files. The design canvas file is shared while the agent runs, so it is passed by path and the backend must see it.
- **Login PATH.** `wsl.exe --exec` and most commands start programs without a login shell, so `gentle-shell` and its Node wouldn't be found. Once per backend the app runs the user's login shell there, interactive (`gentle_core::backend::path_probe`, the same markers as the local combined PATH), and keeps the result; Setup asks again on every check.
- **Paths.** `Backend::path` maps what the app sees to what the backend sees, `Backend::host_path` the way back (what `git` prints, in the same form as the project folder). In WSL, `C:\…` is `/mnt/c/…` and `\\wsl.localhost\<distro>\…` is `/…`, also in the verbatim form Windows canonicalizes a share to (`\\?\UNC\wsl.localhost\…`); through a command, paths are the same, as OrbStack and Lima mount the home folder. A project the backend can't reach is an error on the tab, not a silent fallback. A project inside the distro's own file system is much faster than one under `/mnt/c`, which WSL reads from Windows over 9P.
- **Windows installs seen from WSL.** WSL appends Windows' PATH, so a `gentle-shell` Windows installed answers there too (`/mnt/c/…`, `gentle_core::backend::is_windows_file`). It doesn't count as the distro's: the distro list, Setup and Configuration's Launcher line say only Windows' is visible, Setup offers the Linux install, and an agent tab refuses to start through it (its packages would load over 9P, minutes slower).
- **Terminals.** `Backend::terminal(folder)` starts the backend's login shell in the project folder: `wsl.exe -d <distro> --cd <folder>`, or the prefix with a small `sh` that finds the user's shell. `docker exec` gives the shell a TTY only with `-t`, which the agent's JSONL can't have, so container terminals are line-based; OrbStack and Lima give one.
- **Git and the file views.** `backend::git(cwd, env)` runs `git` where the folder's agents run (in WSL instead of over `\\wsl.localhost`, which is slow). The Files, Changes and Branches views, the Git pane (its reads and every action: fetch, pull, push, branches, tags, cherry-pick, revert, reset, remotes, Git LFS), the palette's branches and the profile pin's worktree identity go through it; the top level and worktree paths git prints read back with `host_path`, pathspecs and new worktree folders go in with `backend::there`. On a Gentle Shell server it runs through `POST /api/git` (below), and the file views read through `backend::fs`. Actions run with `GIT_TERMINAL_PROMPT=0` and never open an editor (`--no-edit`, `core.editor=true` to continue): a remote that needs credentials fails with git's message instead of waiting.
- **Setup.** With a backend saved, `setup::run_checks` checks Node.js, Gentle Shell, its setup marker, a provider (its `auth.json` and `models.json`, or an already installed Claude bridge with Claude Code signed in), git and Engram there (`setup/remote.rs`), never on this computer, and the Setup badge names the backend. Fixes are commands typed in a terminal, which opens in the backend at the user's home there: nvm for Node.js; `npm install -g` for gentle-pi, into `~/.local` when npm's global prefix is root's (a distro's Node); `gentle-shell setup`; `gentle-shell` then `/login` for a provider. `gentle-shell --version`, `upgrade`, `install` (Extensions) and Configuration's version and home lines go through `backend::shell_spec` / `home_shell_spec`.
- **Homes.** In a WSL distro, the app reads and writes that distro's Gentle Shell homes through `\\wsl.localhost` (`pi_rpc::use_backend_homes`, set at start and when the choice changes): Configuration, sessions, usage and profiles see the files the agents use. A conversation picked from that list resumes with its path mapped back (`--session /home/…`).
- **Providers.** Signing in runs where the agents do: the Providers screen offers a terminal there with `gentle-shell` typed, for `/login`, instead of this computer's sign-in helper.
- **Engram, Maestro, Tower and music.** Each installs and runs where agents run (`super::remote::backend()` picks the branch). What the app downloads (Engram's release, the Temurin JRE and Maestro CLI, uv, Tower's source) is fetched and checksum-verified here for the backend's machine (`uname -m`), then copied there: a file with `backend::put_file`, a folder as a tar stream with `backend::put_dir` (only `tar` is needed there; files the app must run are marked executable after, since Windows keeps no Unix modes). The app's things go to `~/.local/share/gentle-shell-gpui` there. Engram goes over the one there, else into `~/.local/bin`, `~/bin` or `~/go/bin` when on the PATH, else `/usr/local/bin` when writable, else `~/.local/bin`. Maestro is registered with that backend's `gentle-shell mcp add` and reaches the devices it sees (Chromium pages; an emulator its `adb` reaches; iOS simulators only on a Mac). Tower is built there with pnpm and served from there, tied to its input inside the backend, so closing the tab stops it; its page opens through the backend's forwarded localhost (WSL2, OrbStack and Lima forward it; a container needs the port published). gentle-stream runs there, its audio through WSLg on Windows; a VM or container has no sound device.
- **Not through the backend:** through a command, Configuration still reads this computer's Gentle Shell home (a VM's or container's isn't reachable as a path); the diagram renderer draws previews here. An SSH command isn't supported: `ssh` joins its arguments into one remote command line.

#### Gentle Shell server (`{"kind": "server"}`)

`gentle-shell serve` (Gentle Shell's `docs/serve.md`, protocol `gentle-shell.serve/v1`) runs one server per agent home that owns `gentle-shell --mode rpc` sessions, so they keep running while no client is connected. The app is one paired device of it.

The app on this computer is the window and the tools that need it (browser, screen, devices, Agent UI); the server owns the agents, their folders, git and terminals. Everything goes through `pi_rpc::serve` with the device's bearer token, and every view that would touch a project's files, git or a shell asks one choke point (`backend::fs`, `backend::git`, `terminal/remote.rs`) which side to use, so the same views work for both.

```mermaid
  S-->>A: device id + token gss_…
  A->>S: GET /api/server (capabilities, platform, home)
  Note over A: address/device/name → settings.json,<br/>token, fp, relay → server-tokens.json (0600)
```

- **Connecting with a code.** Configuration → General → Where agents run → Gentle Shell server shows one field, Code (placeholder `XXXX-XXXX`), and Connect. It takes either code `gentle-shell serve share` shows (`gentle_core::serve::read_code`): the 8-character pairing code (case, spaces and dashes ignored, O read as 0 and I/L as 1, the server's Crockford base32 alphabet; Enter or Connect), or the long connection code it prints as a fallback (it starts with `gsc1.`; pasting one connects by itself). Anything else reads as what to enter.
- **Finding the server for a short code.** The short code names no server, so the app finds the servers on the local network over UDP: from one ephemeral socket it sends `{"t":"gentle-shell/discover","v":1}` to 255.255.255.255 and to each IPv4 network's directed broadcast address on this computer (from its interfaces' addresses and prefixes, read with `sysinfo`), at ports 8787–8796 (`gentle_core::serve::discovery_targets`). A server listening on the network (not loopback) answers on its HTTP port with `{"t":"gentle-shell/here","v":1,"id":"<serverId>","n":"<host name>","p":<http port>}`, plus `"tls":true,"fp":"<certificate fingerprint>"` when it speaks HTTPS (no secret; `gentle_core::serve::read_announce` drops anything else, or longer than 512 bytes; the `fp` is a hint only). Answers are collected for 1.5 s (`pi_rpc::serve::nearby`), then each is checked at `GET <scheme>://<source address>:<p>/.well-known/gentle-shell` (`https` when it announced TLS, accepting whatever certificate it shows and keeping that certificate's fingerprint as `Nearby::fingerprint`): only those saying the same `serverId` count, and a server answering on several interfaces counts once (`gentle_core::serve::pick`). One server: the code is sent there (`pi_rpc::serve::pair_nearby`: over HTTPS only after the [pairing proof](#tls-the-pairing-proof-and-the-relay), then `POST /api/pair` pinned to that certificate) and that address is saved, with the server's name. Several: the section lists them (name and address) under "Several computers answered. Which one showed this code?" and pairs the one clicked. None: "Couldn't find a computer running gentle-shell serve on your network…" (same Wi-Fi? the firewall must allow port 8787, TCP and UDP: on Omarchy `sudo ufw allow 8787`; or paste the long code instead). `403 invalid_code` reads as the code being unknown, used or expired (run `serve share` again); a failed proof as the server not proving it knows the code, which was not sent (`gentle_core::serve::proof_failed`). While it works the section says "Looking for computers on your network…", then "Pairing with <name>…". Discovery doesn't cross subnets, Tailscale or Wi-Fi client isolation: there the long code (or an address) is the way. On macOS the first search may ask for Local Network access.
- **Connecting with the long code.** `gentle-shell serve share` prints it on the server: `gsc1.` + base64url (no padding) of `{"v":1,"id":"<serverId>","n":"<host name>","p":<port>,"a":["<addr>",…],"c":"<pairing code>"[,"fp":"<certificate fingerprint>"][,"r":"gsr://<relay host>:<port>"]}`, where `a` is the server's non-loopback, non-link-local IPv4 addresses, LAN first, then its host name and `<host>.local`; `fp` is there when the server speaks HTTPS, `r` when it registers with a relay. `gentle_core::serve::decode_connection_code` reads it (white space and `=` padding ignored; `CodeError` says what's wrong: not a code, damaged (also a malformed `fp`, or an `r` that isn't `gsr://host:port` or comes without `fp`), a newer version, no server id, no usable address (none and no relay), a bad port or pairing code; addresses that aren't a host name or IP address are skipped, at most 8 kept; with `fp` they are `https://` addresses). `pi_rpc::serve::locate` then asks every address, and the relay, at once for `GET /.well-known/gentle-shell` (no token; `{"schema":"gentle-shell.serve.identity/v1","serverId","name","protocol","version","tls"[,"fp"]}`), over HTTPS pinned to the code's `fp` (the code came from the server itself, so no pairing proof), 1.5 s each and 4 s in all, and the first whose `serverId` is the code's wins (`gentle_core::serve::search`): the pairing code is only ever sent there (`POST /api/pair`, `pi_rpc::serve::pair_code`), and that address is saved as the server's, with the code's `n` as its name. Found only through the relay, the server is saved under its first own address and answers at the relay (`at`) until it is found on the network. While it looks the section says "Looking for <name> on your network…", then "Pairing with <name>…". Nothing answering as a Gentle Shell server reads as "Couldn't find <name> on your network…" (same Wi-Fi? run `serve share` again; a firewall may block the port; with a relay: "Couldn't reach <name> on your network or through its relay…"), only other servers answering as a different server (it restarted: a new code), and `403 invalid_code` as the code having expired or been used. The code is a secret while its pairing code is valid (5 minutes, once); from a server started with `--no-tls` (no `fp`) the connection is plain HTTP, so it is for a network that encrypts by itself.
- **Pairing by address.** Under Enter address manually, the section takes the server's address (`gentle_core::serve::normalize_url`: `http://host[:port]` or `https://host[:port]`, a bare `host:port` gets `http://`; a path or credentials are refused) and the code `gentle-shell serve pair` printed there (a connection code typed in either field connects with it instead). `pi_rpc::serve::pair_at` asks an `http://` address who it is first: a server that speaks HTTPS says so in its identity (`"tls":true`, from this computer) or refuses plain HTTP from the network (`400 tls_required`), and the pairing moves to `https://` with the [pairing proof](#tls-the-pairing-proof-and-the-relay) before the code goes out. Pair sends `POST /api/pair { code, name: "Gentle Shell GPUI on <host>" }`, then `GET /api/server` with the new token. Server errors read as what to do (`gentle_core::serve::error_text`): `403 invalid_code`, `429 rate_limited`, `409 too_many_devices`, `421 bad_host` (the Host the server doesn't answer to), `403 forbidden_origin`, `400 tls_required`, `401` (a revoked device). Once paired the section shows the server's name (its host, or the code's name), address, `serverId`, Gentle Shell version and this device's id, and Unpair.
- **The token.** The device token (`gss_…`) is a secret: `settings.json` keeps only the address, device id and name; the token goes to `server-tokens.json` in the app's folder (`0600`, written beside and renamed in), keyed by address (`features/backend/server.rs`), with how the server is reached beside it (`fp`, the certificate fingerprint pinned at pairing, and `relay`, the `gsr://` relay; `server::trust_of` makes the `pi_rpc::serve::Trust` every client is built with) and the server user's home folder (`home` in `GET /api/server`, which the server tells devices that may operate sessions; `server::home`, `server::known_home`), so new tabs and workspaces know where to start before the server answers. Workspaces and saved tabs name the server by its server id (`server::key`; one saved by address before ids were kept reads as the id once a pairing knows it, `server::key_of`), so pairing the same server again — at another address, or after an unpair — takes the earlier pairing's place (`server::replace_pairing`, matched by id, or by the pinned certificate for a pairing older than ids) and asks the server to replace that device (`POST /api/devices/self/replace`: its terminals become the new pairing's, then it is revoked); the window's tabs and terminals on it follow the new pairing and reattach. Unpair (`server::unpair`) asks the server to remove this device first (`DELETE /api/devices/self`; the server closes its terminals and streams, its agent sessions keep running), then forgets the token here and goes back to this computer; the window's tabs on it let go of their sessions, which a later pairing with the same server picks up again. When the server doesn't answer or is too old, the token is forgotten anyway and Configuration says the server still lists the device, with `gentle-shell serve devices --revoke <id>` to remove it there.
- **When the server's address changes.** A server's computer can get another address (DHCP, another Wi-Fi). Pairing keeps, beside the token, the server's id (`serverId`, which `gentle-shell serve` keeps across restarts), its machine's host name (from the connection code, the discovery answer, or `/.well-known/gentle-shell`'s `name`) and every address it was reached at (the code's `a` too, at most 16). The paired address stays the server's name in `settings.json`, workspaces and saved tabs; where it answers now is `at` beside the token (`server::address`, shown under Address in Configuration). Every client the app builds (`server::client`) is `ServeClient::relocating`: a request that couldn't connect at all (no such host, connection refused or unreachable, connect timeout, a relay without the server; never one the server answered, so nothing runs twice) asks `server::relocate`, which looks for the server, at once, at its known addresses, `<host>` and `<host>.local` on the same port and scheme, then its relay (`gentle_core::serve::relocation_urls`), and by the UDP discovery (`nearby`, by id; what answers is asked again): `pi_rpc::serve::find` asks `GET /.well-known/gentle-shell` with the pinned certificate, which must name the same `serverId`, so the token never goes to another machine, nor to one with another certificate. Found, the address is saved (`at`), every clone of the client (a session's commands and its stream) follows it, and the request is sent again there; the tab doesn't notice. One search runs at a time; one that found nothing waits 20 s before the next. A pairing made before the id was kept learns it on its next `GET /api/server`.

##### TLS, the pairing proof and the relay

A server listening on the network speaks HTTPS with a self-signed certificate it makes on its first run (Gentle Shell's `lib/serve-tls.ts`), and plain HTTP stays only for connections from its own computer; with `--relay gsr://host:port` it also registers with a relay (`gentle-shell relay`, `lib/serve-relay.ts`) that reaches it from anywhere. The app's side is `pi_rpc::serve::tls`, ureq's HTTP over a connector of its own (`LinkConnector`; rustls with ring, the TLS stack the app already had):

- **Pinned TLS.** `https://` connections accept exactly the certificate whose fingerprint (base64url SHA-256 of its DER, `gentle_core::serve::certificate_fingerprint`) the device paired with: no CA and no host name are checked (`PinVerifier`), and the handshake's signature is still verified against that certificate's key. Any other certificate ends the connection before a byte of the request (or the token) is sent, and the request fails with `certificate_changed` and "The server's certificate changed since this device paired with it, so nothing was sent to it: pair again…" (`gentle_core::serve::CERTIFICATE_CHANGED`); it is never taken for a move. Plain HTTP is used only for a server paired without TLS (on this computer, or started with `--no-tls`): a client with a pinned certificate refuses `http://`, and one without refuses `https://`. Every request, event stream, file watch, terminal stream and forwarded page the app reads itself (`ServeClient::open_page`, Engram) goes this way.
- **The pairing proof.** A server found through something anyone can answer (discovery, a typed address) is asked to prove it knows the pairing code before the code goes out (`pi_rpc::serve::prove`): a first connection accepts any certificate and keeps the one seen, sends `POST /api/pair/proof { nonce }` (32 random bytes, base64url), and one of the `proofs` must equal HMAC-SHA256(key, fingerprint ‖ nonce) with key = scrypt(code as the server normalizes it, `"gentle-shell/pair-proof/v1"` ‖ fingerprint, N = 2^15, r = 8, p = 1, 32 bytes), the fingerprint raw (`gentle_core::serve::verify_pair_proof`, the fork's known-answer vector in its tests). Only then is `POST /api/pair` sent, on a connection pinned to that certificate. A connection code's `fp` is pinned as it is.
- **Through a relay.** A `gsr://host:port` address goes to ureq as `https://host:port` (`tls::transport_url`); the connector opens TCP to the relay, sends `{"t":"gsr/client","v":1,"id":"<fingerprint>"}` (plus `"port"` for a forward's listener) and a newline, reads the one answer line (`{"t":"ok"}`, or `{"t":"error","code","message"}`: `offline`, `busy`, `timeout` and `refused` read as a refused connection, so the client looks for the server elsewhere), then runs the same pinned TLS over it, so the relay only sees ciphertext. Sessions, their streams, reattaching after a restart and resuming by `seq` work through it as they do directly.
- **Forwarded pages:** opened through a proxy on this computer (`ServeClient::local_page`; see [forwards](#pages-on-the-servers-loopback-forwards)), which speaks the same pinned TLS and relay; the web view and the browser only see `http://127.0.0.1`.
- **Tests.** `pi-rpc/tests/serve.rs` puts a TLS front (a rustls server with the certificates in `tests/fixtures/serve-tls`, made by the fork's own certificate code) in front of the fake server: the pin and a changed certificate, a typed `http://` address moving to HTTPS after the proof, an impostor that can't prove the code never getting it, and discovery keeping the certificate the handshake showed; `tests/serve/relay.rs` adds a relay in front of that: a session read, resumed and reattached through it, a code found only through its relay, and a relay without the server; `tests/serve/local_pages.rs` opens a stand-in forward behind the front through the local proxy (see forwards). `gentle_core::serve` checks the proof's known-answer vector; `serve::tls` the verifier and the relay's handshake lines. The ignored `pi-rpc/tests/serve_live.rs` (`GENTLE_SHELL_CHECKOUT` = a Gentle Shell checkout) starts a real `gentle-shell relay` and `serve --relay` in a temporary home on loopback, pairs over pinned TLS with the proof, reaches the server through the relay, and loads a `python3 -m http.server` page through a server-level forward and the local proxy, directly and through the relay.

##### Transport: sessions over HTTP and SSE

- **Sessions as backends.** A server tab is a `PiProcess` like any other (`PiProcess::serve`), so the session view, Desktop RPC (still `/gentle:desktop` prompts) and dialogs work unchanged. Starting one sends `POST /api/sessions { cwd, sessionId? }`: `cwd` is the tab's folder as typed, a path on the server, and `sessionId` the Pi session id of a conversation to resume (`gentle_core::serve::pi_session_id`, from the session file's name `<timestamp>_<id>.jsonl`), for `/reload` and restarts. Each command goes to `POST /api/sessions/:id/rpc`, one at a time in order, though one unanswered after 2 s lets the next go (a long `bash` never holds up an `abort`); its answer, which carries the app's id, is read as if the child had printed it. An answer of `202 { pending, id }` (a command longer than the server's 30 s) is settled by the stream's response under that server id. `extension_ui_response` goes through `/rpc` too (`202 { accepted }`). A transport or server failure answers the waiting request with the error.
- **The event stream.** `GET /api/sessions/:id/events` with the bearer header (the server takes it there; tickets are for browsers). `gentle_core::serve::SseParser` frames it, `Stream` keeps the last `seq` and decides each event, `RpcIds` skips the stream's copies of responses (the server sends every command under its own `serve-rpc-N` id and repeats the response there) unless one settles a `202 pending`. A dropped connection, or 45 s without a byte (the server's heartbeat is 20 s), reconnects after 1 s, doubling to 30 s, with `after=<last seq>`; `resync` reconnects at once. `snapshot-required` (records evicted from the replay ring) becomes `Incoming::Resync`, and the tab reads everything again as after opening a session (`reset_conversation`, the Desktop channel's reset and `refresh_state`: `get_state`, `get_messages`, the models, the stats and the Desktop probe). `dialog` events and replays never show a dialog twice. `serve_session_exited` (or a session the server reports exited) ends the tab as an exit; `401`/`403`/`404` on reconnect say why and end it too. Such a tab reads "Disconnected from <server>" (the session was stopped there, or the server stopped) with Start again: a new session in the same folder resuming the conversation (`sessionId`), as `/reload` does.
- **Dialogs answered on another device.** Every device following a session shows its dialogs (`select`, `confirm`, `input`, `editor`); the first answer wins. When another device answers, the server adds `{"type":"serve_dialog_resolved","id"}` to the stream (`Step::DialogResolved` → `Incoming::DialogResolved { id, refused: false }`), and the tab drops that dialog, shows the next one and notes "Answered on another device." in the conversation (`SessionView::dialog_resolved`); the record for an answer this tab sent closes nothing. When this tab answers second, `POST …/rpc` gets `409 dialog_answered`: no error line, the note says "Another device answered this first; the answer here wasn't used." (`refused: true`).
- **What the server offers.** `GET /api/server` lists `capabilities` (`files`, `git`, `uploads`, `terminals`, `server-forwards`, `services`, `print`, …) with the server's `platform`, `arch`, `pathSeparator` and `home`; the app asks once per run (`server::known_info`, `server::offers`; `server::said` for views drawing without asking, `server::forget_info` after installing the terminal host or pairing again). Paths are the server's as they are (no mapping: `host_path` and `there` are identity). Whatever the server doesn't offer shows "This Gentle Shell server can't do that yet: upgrade Gentle Shell there." (`server::UNAVAILABLE`) instead of reading this computer; what never runs on a server (Setup's installs of Engram, Tower and music, `backend::launch_spec` and so `shell_spec`/`home_shell_spec`: `install -l`, `upgrade`) says "Not available on a Gentle Shell server." (`server::NOT_ON_SERVER`). Setup only checks that the server answers this device (`setup::remote::server_checks`), and Providers says to `/login` on the server. The app's own instructions, extensions (Agent UI) and the design canvas file aren't given to server sessions (host tools stand in for them). The client calls are `pi_rpc::serve` (`serve/files.rs`, `serve/services.rs`, `serve/terminals.rs`), tested against a stand-in server in `crates/pi-rpc/tests/serve_api.rs`.

##### Sessions and reattach

Quitting detaches; it never stops anything on the server. Agent tabs save `server: { url, id }` and terminal panes their terminal id, and the next launch reattaches to the same ones:

```mermaid
sequenceDiagram
  participant A as App
  participant S as gentle-shell serve
  participant T as gentle-term-host
  Note over A: Quit: PiProcess::detach, terminal stream dropped
  Note over S,T: session and shell keep running
  A->>S: GET /api/sessions/:id
  alt still running
    A->>S: GET /api/sessions/:id/events?after=…
    A->>S: POST …/rpc get_state, get_messages (conversation rebuilt)
  else gone (stopped, server restarted)
    A->>S: POST /api/sessions { cwd, sessionId } (resumes the Pi session)
  end
  A->>S: GET /api/terminals/:t/stream
  S->>T: attach { term }
  T-->>A: attached + snapshot (screen as it is), then output
  Note over A: a terminal the server no longer has →<br/>POST /api/terminals in the same folder
```

- **Closing and quitting.** Closing a server tab stops its session there (`DELETE /api/sessions/:id`, in the background). Quitting the app leaves every server session running (`SessionView::quit_backend` → `PiProcess::detach`); the pane is saved with `server: { url, id }` (`SavedPane`), and the next launch reattaches: `GET /api/sessions/:id` and, while it still runs, follows it live and reads the state (`get_messages` rebuilds the conversation, so nothing is replayed). A session the server no longer has (stopped, or the server restarted) starts again in the same folder, resuming the Pi session from the saved session file (the server opens it by exact id, `--session-id`, and creates it when Pi never wrote it: a conversation with no messages yet). A server unreachable at that moment is an error on the tab rather than a second session; Start again on it tries once more.
- **A canvas's agent.** The agent floating over a canvas behaves the same: quitting detaches it (`CanvasView`'s quit hook → `quit_backend`), the canvas pane is saved with its `server: { url, id }` (`CanvasView::agent_server_session`) beside the conversation, and on restore the canvas reattaches to it at once, the card hidden (`CanvasView::reattach_agent`), so the agent's `canvas_*` host tool calls reach the canvas again; the Agent button shows it. Closing the card (or the canvas pane) stops the session there.

##### Host tools

A server session can't use the app's files, so the tools that need this computer (its window, screen, simulators, themes) are offered to it as host tools: the server's agent calls them, the app runs them here and answers. Each tab registers them on its own session; another device following the same session never runs this device's calls.

| Tool | Offered when | Runs | Answers with |
|---|---|---|---|
| `open_page` | always | the window's tray, or the user's browser per Devices › Browser; a server-loopback URL through a forward | text |
| `browser` | always | the window's browser driver (`gentle-browser`'s operations) | text, screenshots as images |
| `screen` | always | `gentle-screen` on this computer (launch, click, type, …) | text, screenshots as images |
| `canvas_read` / `canvas_edit` / `canvas_shot` | the agent sits beside a canvas | the open canvas, in-process | text, shot as image |
| `device` | Devices › Use devices and Agents can use devices | the device panel and `agent-device` here | text, screenshots as images |
| `maestro` | as `device`, and the Maestro CLI installed here | `maestro --device <id> test/hierarchy`, simulator/emulator screenshots | pass/fail and output, JSON, image |
| `app_theme` | always | the app's themes folder (guide, examples, write, previews) | text, previews as images |
| `gentle_ui` | the server takes `host_message` and `set_host_context`, Agent UI not Off | `gentle_core::genui::host` in the app | summary text + surface `details` |

All of them need the server's Desktop RPC to advertise `set_host_tools`; without it the session runs with no app tools.

- **Host tools: the app's tools, run here.** A server session gets neither the app's `agent-instructions.md` nor its extensions (they are files on this computer). Instead, when its Gentle Shell advertises `set_host_tools` (Desktop RPC, `gentle-shell.desktop-rpc/v1`), the tab offers the app's tools as host tools once the channel's `capabilities` answer, and again after the stream reconnects or the session switches (`features/session/host_tools.rs`): `set_host_tools { provider: "desktop", tools }` (the server replaces `provider` with this device's id). The tools and their guidance (`features/host_tools.rs`: description plus `guidelines`, which Gentle Shell hands to the model as Pi's tool guidelines while they are registered) are:
  - `open_page { url }`: what `gentle-open` does — the page opens in the window's tray, or in the user's browser when Configuration › Devices › Browser says so. A URL on the server's loopback opens through a forward (above); the guidelines tell the agent to pass its dev server's `localhost` URL as it is, over plain HTTP.
  - `browser { op, … }`: `gentle-browser`'s operations (open, tabs, goto, back, forward, reload, state, eval, snapshot, the element actions, wait, screenshot, pick, close, release), run by the window's driver (`Workspace::browser_request`, as the single-instance server runs them for the CLI). A screenshot comes back as an image.
  - `screen { op, … }`: `gentle-screen`'s operations (launch, windows, screenshot, click, type, key, scroll, quit), run in this process (`screen::cli::run_op`) on this computer; its description says so (a `launch` command and `cwd` are this computer's). A screenshot comes back as an image.
  - `canvas_read`, `canvas_edit`, `canvas_shot`: only for an agent opened beside a canvas. The open canvas answers in-process (`CanvasView` subscribes to its agent's `SessionEvent::HostTool`) with the same `gentle_core::canvas::agent` answers the `.agent` folder gets; a shot comes back as an image. The canvas extension's per-turn role section becomes `canvas_read`'s guidelines.
  - `device { action, device?, app?, target?, text?, shutdown? }` (`features/host_tools/device.rs`), offered only while Configuration › Devices has Use devices and Agents can use devices on: `list`, `open`, `close` are `gentle-device`'s (the window runs the same request through `Workspace::device_request`, then the call waits for the hub and the device as `gentle-device` does, `devices::cli::wait_ready`); `launch <app>`, `snapshot`, `press <target>`, `fill <target> <text>`, `screenshot` and `install <app>` run `agent-device open|snapshot -i|press … --settle|fill … --settle|screenshot <tmp>|install` in a child here, pinned to the device as `gentle-device open` prints (`--platform … --udid|--serial <id>`); a screenshot comes back as an image. `install` takes an absolute path on this computer or an http(s) URL the app downloads to a temporary folder (≤ 4 GiB; a `.zip` is unpacked to the `.app`/`.ipa`/`.apk` inside); its guidelines say a build on the server's disk isn't here, so the agent must make it reachable by URL. The instructions' "never xcrun simctl, emulator -avd, adb shell input" become guidelines. Operands that start with `-` are refused.
  - `maestro { action, yaml?, device? }` (`features/host_tools/maestro.rs`), offered only while devices are on for agents (as `device`) and the Maestro CLI is installed on this computer: Maestro runs here, on the device panel's open simulator or emulator (`device` names one; it may be left out when exactly one is open). `run_flow` writes the agent's flow (`appId: …`, `---`, commands; at most 256 KB) to a temp file, runs `maestro --device <id> test <file>` (5 minutes at most) and answers with whether it passed and Maestro's output (colours stripped, the last 24 KB), deleting the file after; `hierarchy` answers `maestro --device <id> hierarchy` as trimmed one-line JSON (64 KB at most); `screenshot` answers an image taken with `xcrun simctl io <udid> screenshot` or `adb -s <serial> exec-out screencap -p` (Maestro has no screenshot command outside a flow). One run at a time; the environment is the app's toolchain (`setup::maestro::command_here`: Java 17+, `PATH`, `DEVELOPER_DIR`, `ANDROID_HOME`, analytics off). Its guidelines tell the agent never to run the `maestro` CLI or a Maestro MCP on its own machine and to inline steps that name files (they aren't on this computer). Whether it is offered is checked when tools are offered (start, reconnect) and again on every call.
  - `app_theme { action, name?, theme?, scene?, stem? }` (`features/host_tools/themes.rs`): the theme workflow of the instructions without the folder's paths. `guide` is the GUIDE.md text (`devices::theme_guide`) with a note mapping its file names onto the actions; `examples` lists the shipped example themes and built-in scenes, `example <name>` returns their text; `write` saves `<stem>.json` (and the scene as `<stem>.js`, which `background.scene` then names) in the app's themes folder only after `parse_pi_theme` reads it, backdrop included, from a scratch folder (else nothing is saved); `preview <stem>` returns `previews/<stem>.txt` and `scene-error.txt` as text and `.png`, `.grid.png`, `.effects.png` as images.
  - `gentle_ui { action, id?, title?, kind?, spec?, patch?, wait? }` (Agent UI), offered when the server also takes `host_message` and `set_host_context` and Agent UI isn't Off: the generative UI extension, run by the app itself (`gentle_core::genui::host`, `features/session/host_genui.rs`); see [On a Gentle Shell server](#on-a-gentle-shell-server-gentle_ui-as-a-host-tool) under Generative UI. Its guidelines are the extension's rules for the current mode, and an Agent UI change offers the tools again with the new ones.

  A call arrives as the `host_tool_call` event `{ callId, provider, tool, args }` (after a reconnect the server may re-send one as an SSE frame `event: host_tool_call`, which `gentle_core::serve::Stream` reads as a record without moving the cursor); each `callId` runs once, and only when its `provider` is this device's id (the paired `device` the backend choice keeps), since other devices following the same session register their own tools. The ignored live check `live_registration_on_a_server` (`features/host_tools.rs`; `GENTLE_SHELL_LIVE_SERVE_URL`, `_TOKEN`, `_CWD`) registers every tool on a running `gentle-shell serve`, checks a stray result (with `details`) is refused with `unknown_call`, and sends a `host_message` (no turn) and a `set_host_context` set and cleared. Its result goes back as `host_tool_result { callId, content: [text | image], isError?, details? }` (8 MiB of content at most; over that, an error result says so; `details`, at most 1 MiB, becomes the Pi tool result's: `gentle_ui` sends its surface there). Every request goes to the server's `POST /api/sessions/:id/desktop` (`PiProcess::desktop`), never as `/gentle:desktop` prompts: the server checks which device provides a tool and answers its calls, and refuses them on `/rpc`. `host_tool_cancel { callId }` (a stopped turn, a cancelled or expired call) drops the call: a step already running finishes, and no result is sent. A call to a tool the app doesn't have, bad arguments or a driver error answer `isError: true` with a readable message; an `unknown_call`/`already_answered` answer to a result (the call is over) is ignored, any other failure is a warning in the conversation, as is a tool the server rejected at registration. Tabs on this computer, in WSL or through a command keep the instructions and extensions they launch with and register nothing.

  **Long calls stay alive.** A server fails a host tool call nobody answered after 10 minutes. When its `capabilities` list `host_tool_progress`, the tab sends `host_tool_progress { callId }` every 60 s (`HOST_TOOL_PROGRESS_EVERY`) for each call it still works on (a `gentle_ui` review waiting for decisions, a browser wait, a Maestro flow, a device download), and the server restarts that call's 10 minutes each time, with no cap on the total. The heartbeat (`HostCalls::due`/`next_beat`, one loop per tab, timed on the executor's clock) stops once the call is answered, cancelled or the server says it no longer holds it (`unknown_call`/`already_answered`), and when the backend is replaced or exits; a failed send waits for the next beat. A hung app, or one that lost the server, stops sending and the call fails after 10 minutes as before. An older server gets no progress.

Not offered to server sessions, by design: the app's `agent-instructions.md`, its extensions and the design canvas file (they are files on this computer; the host tools above stand in for them), a Maestro MCP server and the server's themes:

- **Maestro.** A server session gets no Maestro MCP server (one would run Maestro on the server, far from the simulators): Settings → UI testing installs Java and the Maestro CLI on this computer only and offers the `maestro` host tool instead (above).
- **Themes** stay the app's own: the theme catalog reads this computer's Pi themes and the app's themes folder, never the server's home, and `app_theme` writes to the app's folder.

##### Host tools in a tab on this computer

A Gentle Shell new enough to have `serve` takes the same host tools over its stdio, so a tab here (or in WSL, or through a command) gets them too, in place of the app's instructions and extensions:

- **The probe.** Before a tab starts, `backend::takes_host_tools` asks `<launcher> serve --help` (`pi_rpc::probe_host_tools`, 5 s at most, stdin closed). Only that: a launcher older than `serve` hands any other `serve …` (`serve status`) to Pi, which would send it to the model as a prompt, while `--help` makes Pi print its own help. The launcher supports host tools when a `Usage:` line names `gentle-shell … serve` (`pi_rpc::launch::names_serve`, the fork's `SERVE_HELP`); Pi's help never does. The answer is cached per launcher file and its stamp (`pi_rpc::takes_host_tools`; a self-contained install's `gentle-pi/package.json`), per backend for WSL and commands (`backend::forget_paths` and `forget_versions` drop it), and a launcher that doesn't answer in time counts as one without.
- **The launch.** Such a tab starts with `LaunchSpec::without_app_tools`: the `--append-system-prompt` and `--extension` arguments after `--mode rpc` (the app's own) are left out; `GENTLE_SHELL_ARGS` before it stay. The tab is marked (`state::Backend::host_tools`), and once its Desktop channel advertises `set_host_tools` it registers the tools as a server tab does, under provider `desktop` (nothing replaces it here, so calls with that provider are this tab's), and runs `gentle_ui` itself when `host_message` and `set_host_context` are advertised. An older launcher keeps the instructions and extensions, and registers nothing.
- **Desktop RPC over stdio.** `PiProcess::desktop` sends `set_host_tools`, `host_tool_result`, `host_tool_progress`, `host_message` and `set_host_context` to a child as the `/gentle:desktop <json>` prompt on its stdin, as `gentle-shell serve` does with its own children. The stdout reader hands the `gentle-desktop-rpc` widget response whose `requestId` such a call waits for to that call (30 s at most) instead of `incoming`, so the tab's Desktop channel never sees it (a response has no `seq`; events, `host_tool_call` included, still go through the channel in order). A prompt answered with any disposition but `handled` fails the call at once. Tested with a fake child (`pi-rpc/tests/desktop_stdio.rs`: this test binary itself, so on every system).
- **Wording.** The descriptions and guidelines follow where the agent runs (`host_tools::Place`): on this computer nothing mentions a server or a forward (a `localhost` page opens as it is; `device install` takes a local build path; a Maestro flow's files by absolute path), in WSL or a container they say the app runs outside it, and a server's keep their wording.
- **Maestro.** With such a Gentle Shell here, Settings → UI testing installs Java and the Maestro CLI and registers no MCP server: the agents get the `maestro` host tool. A `maestro` MCP server registered before still shows, so Disconnect removes it.

##### Pages on the server's loopback: forwards

- **Pages on the server's loopback: forwards.** A page a server session names on its own loopback (`localhost`, `*.localhost`, `127.0.0.0/8`, `[::1]`, or the `0.0.0.0`/`[::]` a dev server prints) is the server's, never this computer's, so it never opens as it is. `gentle_core::serve::server_page` sorts each URL a server tab gives: elsewhere (opens as it is), on the loopback (`port`, and the path with its query and fragment, non-ASCII and spaces percent-encoded, a leading `//` dropped, at most 2048 bytes), or unreachable (`https` on loopback: a forward carries plain HTTP). The window (`Workspace::open_session_page`, `workspace/stages.rs`) does it for the design canvas (`design_canvas`, its notify and tool result), `open_page`, a loopback URL in a tool's output or notice, `/web <url>` typed in a server tab (nothing runs on this computer's `localhost` for it), and the `browser` host tool's `open`/`goto` (`session_browser_request`): `backend::server::page_url` sends `POST /api/sessions/:id/forwards { port, path }` (`ServeClient::forward`); the server returns the forward's `url`: its own listener port on the host this device reached the server at, the path, and a single-use `gs_ticket` (60 s) the first visit trades for a per-forward cookie. The card (or the browser outside the app) opens it through this computer's proxy for the forward (next item). The server reuses this device's forward of a port and mints a new ticket on every call, so each open asks again; a card shows one page whatever link opened it (`BrowserPanel::source` keeps the server's URL, `stage_for` matches it). A refused forward (`invalid_port`, `too_many_forwards`, `session_exited`, the session gone, unreachable) leaves the card saying "This page didn't open" with the server's words (`BrowserPanel::refuse`; no web view runs), in the tray for an agent's page, or a notice when agent pages open outside the app; the next link for that page shows it there. Forwards close on the server when the session ends, the device is revoked, or after 12 h unused.
- **Opening a forward on this computer.** The forward's link (`https://<host>:<listenPort>…`, or the relay's host through one) can't go to the web view or the browser as it is: they don't know the server's pinned, self-signed certificate, and a relay's host isn't the server. So `page_url` and `tower` hand them `ServeClient::local_page(forward)` (`pi_rpc::serve::local`): `http://127.0.0.1:<local>/<path>?gs_ticket=…`, served by a proxy listening on `127.0.0.1:<random>` that carries each connection to the forward's listener over the same pinned TLS (`tls::Link::open`), through the relay with the forward's port when the server is reached through one. A plain-HTTP server's link opens as it is. One proxy per forward (by fingerprint and forward id), reused, so a page opened again keeps its origin and cookies. The forward checks `Host` against the server's names for its port and `Origin` against its own, so the proxy reads each HTTP/1.1 head on a kept-alive connection: `Host` becomes the link's `host:port`, an `Origin` or `Referer` of the local page becomes `https://<host:port>` (another origin passes as it is, and the forward refuses it), and a `Location`/`Content-Location` back at the forward points here again. Bodies pass as they come (lengths, chunked, SSE streams); after a `101` a WebSocket's bytes go both ways untouched. A request whose `Host` isn't `127.0.0.1:<local>` or `localhost:<local>` gets `421` and never reaches the server (DNS rebinding). The proxy closes, with its connections, when the last `WebSurface` showing it drops its `LocalHold` (`hold_local_page`: a card closed or sent elsewhere, a Tower tab closed), when the forward is gone (its listener refuses, or the relay answers `refused`: the page gets a `502` saying to open it again), and after 12 h unheld with no connection and no request (a page opened in the browser outside the app). A changed certificate never reaches the page: `502` with the certificate message. `tests/serve/local_pages.rs` covers keep-alive with the ticket, cookie, redirects, `HEAD`, length and chunked bodies, SSE, a WebSocket, the `Host`/`Origin` rules, a changed certificate, the relay, a closed forward and closing with the last holder.

##### Gentle Tower

- **Gentle Tower.** A Tower tab for a server folder sends `POST /api/tower` (`ServeClient::tower`, `backend::server::tower`): the server starts Gentle Tower on its own loopback once, for every device, and answers with a forward to it (Tower's `/<token>/` path and a ticket), which the tab loads through this computer's proxy for it (closed with the tab). Closing the tab leaves Tower running there. The server's message shows when it can't start it (`503 tower_unavailable`, for one its web app wasn't built for; building it here doesn't apply), and a server without the route says to upgrade Gentle Shell there.

##### Folders and workspaces

- **Folders.** A folder on this computer is no folder on the server, so while agents run on one (`backend::saved()`), a workspace records the server it was opened on (`Space::server`, saved as `server` in `workspaces.json`; older ones are read from their panes' server sessions). A new agent tab or split starts in the focused agent's folder when that agent runs on the server, else in the workspace's root when the workspace is that server's, else in the server's home (`Workspace::new_agent_cwd`, `gentle_core::serve::tab_folder`); the first workspace of a fresh app on a server is its home. Server folders are picked in a server folder browser, the ⌘O explorer (`ExplorerView`, `Purpose::Open`/`Choose`) listing the server's folders with `/api/fs/list` from its home (`~` goes there): ⌘K's All and Workspaces offer "Open folder on <server>…", which opens it, and, for a typed absolute path, "Open “/path” on <server>" (`PaletteAction::ShowServerFolder`); New workspace, Create workspace from folder… and the sidebar's Change folder pick with the same browser instead of this computer's folder picker (`show_server_folder` keeps the server path as it is, never canonicalized here). Opening a folder, typed or browsed, shows the workspace already there for it, as a local folder does: one of the same server whose root has the same `folder_key` (`Workspace::space_for`, `workspaces::find_root`; a workspace of this computer or of another server at the same path is another one). New workspace and Create workspace from folder… still always create one. A tab whose folder the server doesn't have (`400 invalid_cwd`) offers "Open in your home on <server>" (`SessionView::change_cwd` to the home) and "Open another folder on <server>…" (`SessionEvent::OpenServerFolder`) beside Start again.

##### Files

- **Files** (`backend::fs`, capability `files`): the choke point for every view that reads or changes a project's files (`at(path)` is `Fs::Local` or `Fs::Server(client)`; `metadata`, `exists`, `is_dir`, `is_file`, `entry_exists`, `canonicalize`, `read`, `read_dir`, `create_dir`, `create_dir_all`, `create_new`, `rename`, `remove_all`, `copy_all`; server errors keep their kind, `io_error`). The Files tree lists with `/api/fs/list` and dims what `git check-ignore -- <names>` (batches of 250, `GIT_LITERAL_PATHSPECS=1`) reports ignored (outside a repository nothing is dimmed); `.git` stays hidden. It follows the server folder with one `/api/fs/watch` stream while the Files tab shows (a changed path and its parent reload; an overflow, or a reconnect after 1 s doubling to 30 s, reloads everything), so a change there appears within about a second. New, rename, delete and copy/paste go through `/api/fs/mkdir|write?create_only=1|rename|remove`; a server has no Trash, so Delete… asks first; copying follows a link to a file and refuses links to folders and special files. The editor reads with `/api/fs/read` (8 MiB chunks, 64 MiB at most) and saves with `PUT /api/fs/write` and `If-Match: <etag>`: a file changed on the server meanwhile (`412 changed`) becomes the usual conflict, "Changed on the server" with Reload / Keep mine, never a silent overwrite; outside writes are polled by etag (`fs/stat`, every 0.8 s focused, 5 s otherwise). Markdown previews fetch relative images from the server; Open with Default App, Reveal in Finder and Open in <editor> aren't offered for server files. ⌘K Files lists `git ls-files --cached --others --exclude-standard -z`, outside a repository it searches names with `/api/fs/search` as you type. A restored file pane checks its file on the server.

##### Git

- **git** (`backend::git`, capability `git`). For a server folder `Git::output` sends `POST /api/git { cwd, args, env }` (the server runs git without a shell, a terminal or a prompt; `env` keeps only the names it allows, so `GIT_TERMINAL_PROMPT=0` is its own) and decodes `stdout`/`stderr` (base64); `success` is exit code 0, not truncated, not timed out. So Changes, Branches, the Git pane and its actions, the palette's branches, the profile pin's worktree identity (`--path-format=absolute`, realpath through `fs/stat`), Review and the staged diff a commit message is written from work unchanged. The Git pane's "in progress" check (`MERGE_HEAD`, `rebase-merge`, …) stats the server's git dir; new worktree folders are checked there. Reads need `sessions:read`, anything else `sessions:operate`; network commands may take up to 10 minutes (the client waits 11).
- **Commit messages** (`files/changes.rs`, capability `print`). For a server folder the Changes pane's message is written on the server: `POST /api/print { cwd, prompt }` (`ServeClient::print`) runs the server's `gentle-shell --print --no-session --no-tools` in the repository with the same prompt a local folder gets (Conventional Commits, from the staged diff), and its `text` is read as the local stdout is (`parse_commit_message`). The server stops it after 120 s; the client waits up to 11 minutes. Its errors read as what happened (`print_failed` with the stderr tail, `print_timeout`, `output_too_large`, `too_many_prints`); a server without `print` says `server::UNAVAILABLE`.

##### Terminals and the terminal host

- **Terminals** (`terminal/remote.rs`, capability `terminals`, the device's `terminal` scope). A terminal pane in a server folder runs one of the server's persistent terminals (Gentle Shell's `docs/serve.md`, Persistent terminals) in the app's alacritty view: `POST /api/terminals { cwd, cols, rows }` (the server user's login shell), then a thread follows `GET /api/terminals/:t/stream`: `attached` with a snapshot resets the emulator and draws it, `output` is fed through alacritty's parser from the last offset (bytes already drawn are skipped), a dropped connection or `overflow` resumes with `from=<last offset>` (backoff 250 ms to 5 s), `title` names the pane, `exit` closes it like a local shell's, the host going away shows in the pane. Keys, pastes, IME and the emulator's own replies go to `…/input` (batched), size changes to `…/resize` once they settle (120 ms). The pane saves its terminal id (`terminal` in `SavedPane`): quitting the app detaches (the shell keeps running in the server's `gentle-term-host`), and the next launch reattaches with the screen replayed; a terminal the server no longer has (or one that exited) is replaced by a fresh one in the same folder. Closing the pane (⌘W, its close button, `exit`, closing its tab or workspace) deletes it there (`DELETE /api/terminals/:t`), as closing a local pane ends its shell; reopening a closed pane opens a new shell. Ctrl+C twice doesn't close a server terminal (the app can't tell its shell is idle), and the title fallback is the folder's name. Without the capability the pane asks `GET /api/term-host`: an older server shows `UNAVAILABLE`; a server without a terminal host shows "Install terminal support on <server>" with, in order, Install from this Mac (or this computer: only when the server's platform and arch are this build's, and a `gentle-term-host` was built with the app, `built_host`: beside its executable, where `packaging/macos/bundle.sh` puts it in the bundle's `Contents/MacOS`, else for a development build the newest in the cargo target folder it runs from, `target/*/` or `target/<triple>/*/`), Choose binary… (any file you point to) and the build steps for the server. Nothing is downloaded. The pane shows the file and its SHA-256 (the app's own build before you choose, then the one being installed); both upload with `PUT /api/term-host` and that SHA-256 (`x-sha256`), which needs a device paired with the `admin` scope (`gentle-shell serve pair --scope sessions:read,sessions:operate,terminal,admin`); a refusal says so. For a server of another kind, build it there from a checkout of this app's branch of gentle-shell-gpui (it has `crates/term-host`), `cargo build --release -p gentle-term-host`, and put `target/release/gentle-term-host` (`.exe` on Windows) in `<agent home>/serve/bin` or on the server's `PATH` (or point `GENTLE_TERM_HOST` at it); `serve` finds it there. A device paired before terminals existed (no `terminal` scope: `403`) gets "Pair again to allow terminals" with the Code field (`settings::ServerConnect`); the new token replaces the old one.

##### Attachments

- **Attachments** (`session/attachments.rs`, capability `uploads`). A file that isn't an image, dropped, picked or pasted into a server tab, is uploaded with `POST /api/uploads?name=` and its server path (`<agent home>/serve/uploads/<device>/<random>/<name>`, kept 7 days; quoted when it has spaces) goes into the prompt; images keep travelling inline. A server without uploads, or a failed upload, says so and sends nothing (never this computer's path).

##### Sessions list

- **Sessions** (`features/sessions`). For a server folder the Sessions browser lists and opens conversations only through an agent tab's Gentle Shell (`list_sessions`, `switch_session`); without one it says to open an agent tab there and never reads this computer's session files.

##### Memories

- **Memories** (`features/memory`, capability `services`). For a server folder the memory screen reads the server's Engram: `GET /api/services` → `engram` (`available`, `forwardable`, `via: "forwards"`) → `POST /api/forwards { port, path: "/" }` → `pi_rpc::serve::ForwardedPage` visits the link once, trades its single-use ticket for the forward's `gs_fwd_<id>` cookie (the `303`) and sends Engram's GETs with it (kept per server; a `401` or a dropped connection opens a new forward once). When Engram isn't there or can't be forwarded the screen says why; it never falls back to this computer's Engram or `ENGRAM_URL`.

##### Configuration, Profiles and Usage

- **Configuration, Profiles and Usage on a server** (`settings/remote.rs`). While agents run on a Gentle Shell server, these screens never read or write this computer's Gentle Shell home, run its `gentle-shell`, or start its login helper (a server tab doesn't read its permission default or banner there either). They read the server's Gentle Shell over Desktop RPC (`get_config`/`set_config` for persona, banner, notifications, profiles and the Profiles stores; `get_status`, `get_auth_status`, `get_update_status`, `get_permission_mode`, background subagents, `list_agent_definitions`, `apply_profile`, subscription usage and `get_usage_stats`), each only when the server advertises it. The General page shows the server's home folder and version from `GET /api/server`. The requests go through the active agent tab when it runs on that server (`ControlSession`, `control_for`); otherwise the screen starts its own hidden `SessionView` in the server's home folder when it opens and stops it (`DELETE /api/sessions/:id`, as closing a tab does) when it closes or the app quits. Signing in, API keys, packages and upgrading Gentle Shell happen on the server too, when it offers them (below); anything else without a Desktop RPC method — Pi's model defaults, `models.json`, `mcp.json` and the Claude bridge plan, and those four on an older server — shows "Do this on <server>: run <command>" instead of acting on this computer.
- **Signing in on a server** (`settings/server_sign_in.rs`, Models › Sign-ins; `login_start`, `login_complete`, `login_cancel`, `set_api_key`, `remove_credentials`). Each provider in `get_auth_status` says how it signs in (`loginKinds`): **Sign in** for `oauth`/`device`, **API key** for `api_key`, and **Remove** for stored credentials. A sign-in runs Pi's own login on the server; its steps arrive as `login_prompt` events and its end as `login_finished` (the events go to `session/accounts.rs` whichever request is pending, and the screen keeps only its own `loginId`, buffering what came before `login_start` answered). `open_url` opens the page in a browser card inside the section (popups load in it); when the login waits for the provider's redirect to the server's loopback callback (`redirectPrefix`, e.g. `http://localhost:1455/`), the card never loads a URL starting with it (`gentle_core::sign_in::is_login_redirect`, the web view's navigation handler, `WebSurface::catch_login_redirects`) and sends the whole URL with `login_complete`, exactly what that callback would have received. **Open in my browser** is the fallback: paste the code, or the address the browser ended on, in the field. `device_code` shows the code with **Copy** and the verification page in the card; `input` is a field (masked when `secret`) or its `options` as buttons; `progress` lines are listed; **Cancel** sends `login_cancel`. On success the server saves the credentials and reloads them in its sessions; the app reads the sign-ins again and its server tabs run `reload_credentials`. A key typed for `set_api_key` is cleared from the field at once and never shown or logged (`Secret`, and `DesktopRequest`'s `Debug` leaves out the payload of `set_api_key` and `login_complete`).
- **Packages on a server** (`settings/server_packages.rs`, Extensions › Packages; `list_packages`, `install_package`, `remove_package`). The list is the server's configured packages with their version, scope and update chip; **Install on <server>** takes any source the CLI takes and each package's trash button removes it. The server validates and reloads as `gentle-shell install|remove` does; the job's output streams as `package_progress` lines until `package_finished`, then the list and the update status are read again. One job at a time from the screen.
- **Upgrading Gentle Shell on a server** (`settings/server_upgrade.rs`, `pi_rpc::serve::upgrade`). With the `upgrade` capability in `GET /api/server` and the `admin` scope on this device's token (`device.scopes`), the Updates offer cards (and a button when none shows) read **Update Gentle Shell on <server>**: `POST /api/upgrade { channel? }` (`main` for the main-commit card) starts the job (`409 upgrade_running` while another runs) and `GET /api/upgrade/:job/stream` streams its `line`s until `finished`. On success `serve` restarts itself: its sessions and terminal host keep running and the app's streams reconnect on their own. The screen polls `GET /api/server` until the server answers again (it was away, or reports another version) and shows the version it runs, then reads the update status again. Without the capability or the scope it says "Do this on <server>: run gentle-shell upgrade".

##### First run

- **First run without Gentle Shell.** The welcome screen and Setup & requirements (`OnboardingView::new`/`sequence`) show "Connect to a Gentle Shell server" above the steps: the same Code field, nearby-server list and Enter address manually as Configuration (`settings::ServerConnect`, which emits `ConnectEvent::Paired` and is shared with Where agents run). Pairing there saves the server as where agents run and looks again: Setup then only checks the server (`setup::remote::server_checks`), nothing is offered to install on this computer (no Node.js, no Gentle Shell), and `OnboardingEvent::RunsOnChanged` moves the shown workspace to the server's home (unless it is already one of its folders) and starts the agent tabs that never came up again there. On a server the card says so and offers "Set up this computer instead". The welcome banner doesn't read this computer's Gentle Shell home then.

##### Limits

- **Trusted network only.** The server speaks plain HTTP; codes, tokens and forwarded pages travel unencrypted. Use it on a home network, or over a tunnel (`ssh -L`, a VPN) with Enter address manually. A forward carries plain HTTP only: an `https://localhost` page on the server can't open.
- **Discovery is one LAN.** The short code needs UDP broadcast to reach the server: not across subnets, Tailscale or Wi-Fi client isolation (use the long code or an address there). macOS may ask for Local Network access on the first search.
- **Terminal host binaries.** Installing never depends on published assets: the app offers its own build when it fits the server (the macOS app bundles one for a Mac server of the same kind; a development build offers the one in its target folder), any file you pick, or the build command for the server. On Windows the host runs shells in a ConPTY and `serve` reaches it over loopback TCP with a token.
- **`gentle_ui` reviews that wait** keep waiting as long as the app is open and connected (it sends `host_tool_progress`). On an older server without it, they give up after 9 minutes (that server fails an unanswered host tool call after 10); later decisions arrive as messages.
- **Server-side retention.** Forwards close after 12 h unused, uploads are kept 7 days, the editor opens files up to 64 MiB, git network commands stop after 10 minutes.
- **Older servers.** Each feature checks the server's `capabilities`; what an older Gentle Shell lacks says to upgrade it there instead of falling back to this computer. Terminals need a device paired with the `terminal` scope; installing the terminal host from the app needs `admin`.
- **Ctrl+C twice** doesn't close a server terminal (the app can't tell its shell is idle); `exit` or ⌘W does.

## Homes: `crates/pi-rpc/src/home.rs`

`resolve_homes() -> Homes { agent, config }` replicates gentle-pi's `resolveHome` (`lib/gentle-shell-launcher.ts`). It is cached until the `Stamp` of the launcher config (`launcher_config_path()`: `GENTLE_SHELL_CONFIG` or `~/.gentle-shell/config.json`) changes.

gentle-ai's managed install, when it is the launcher chosen without the PATH (`GENTLE_SHELL_BIN` or its own folder, `chosen_managed_install`), fixes both, whatever the app inherited, as its launch environment does: `agent` = `<root>\agent`, `config` = `<root>\config` (not `config\gentle-ai`: it sets `GENTLE_PI_CONFIG_HOME`), and the launcher config is `<root>\config\gentle-shell.json`. A managed install reached only through the PATH is launched correctly but these homes do not follow it; gentle-ai only installs it in its own folder.

Otherwise, `agent` (the Pi directory: `auth.json`, `models.json`, `settings.json`, `sessions/`), in order:

| Source | Result | Isolated? |
| --- | --- | --- |
| `--link` in `GENTLE_SHELL_ARGS` | `user_pi_home()`: `GENTLE_SHELL_USER_PI_HOME`, `PI_CODING_AGENT_DIR` or `~/.pi/agent` | No |
| `--isolated` | `GENTLE_SHELL_HOME` or `~/.gentle-shell/agent` | Yes |
| `--home <dir>` | `<dir>` | No |
| `~/.gentle-shell/config.json` `mode`: `link` / `path` (`dir`) / `isolated` | Same as above | Depends on mode |
| Nothing | Isolated by default | Yes |

`config` (Gentle AI config: `profiles.json`, `permission-mode.json`, …), in `config_home`:

1. `GENTLE_PI_CONFIG_HOME`, if not empty.
2. If there is no `GENTLE_SHELL_BIN` and the self-contained install exists: `<prefix>/config/gentle-ai`.
3. If the home is isolated and is exactly `~/.gentle-shell/agent`: `~/.gentle-shell/gentle-ai`.
4. Otherwise: `~/.pi/gentle-ai`.

`adopt_standalone_config()` is called once in `main.rs` before the window opens. The 4.7 install no longer reads `~/.gentle-shell/gentle-ai`; this function copies the missing files into the new folder (recursively, skipping `.lock` and `.tmp`, never overwriting) and leaves the `.adopted-standalone-config` marker so it does not run again. The old folder is left untouched.

Any feature that reads Gentle Shell configuration starts from `pi_rpc::resolve_homes()`; paths are never rebuilt by hand.

### The `gentle-pi` and Pi packages

`gentle_pi_root(spec)` is the `gentle-pi` package a launch runs; the profiles screen (built-in agents), the themes (`themes/`) and the Companion setup check (`.gentle-ai/v<pin>`) read it. A self-contained or managed install names it (`spec.bundled.package`). Otherwise `launch::launcher_script(spec.launcher)` finds the script the launcher runs, by its real path (links and junctions followed to the end):

| Launcher | How |
| --- | --- |
| npm or yarn on macOS and Linux: `<prefix>/bin/gentle-shell`, a link to `gentle-pi/bin/gentle-shell.mjs` | The launcher's real path is the script. |
| pnpm's POSIX shim (every OS) | Its `# cmd-shim-target=<absolute path>` line. |
| `.cmd` shims on Windows: pnpm and yarn (`@zkochan/cmd-shim`, pnpm 11's own copy), npm (`cmd-shim`); `.ps1` and older POSIX shims | The quoted Node script (`.mjs`, `.cjs`, `.js`) relative to the shim's folder: `"%~dp0\<path>"` (pnpm 11 writes `%` as `%%`), `"%dp0%\<path>"`, `"$basedir/<path>"`, `"$basedir_win/<path>"`, or absolute. |

`shim_script` is the pure parser of those formats. The package is the nearest folder above the script with a `package.json`, when its `name` is `gentle-pi`. A pnpm global install (the web installer's `main` channel: `pnpm add -g gentle-pi-<v>.tgz`) lands in pnpm's store, `…\store\v11\links\@\gentle-pi\<v>\<hash>\node_modules\gentle-pi`, with its dependencies as siblings in that `node_modules`.

`pi_package(spec)` finds `@earendil-works/pi-coding-agent` (with `dist/index.js`) from that root as Node does (`pi_candidates`): `node_modules` in the package and in every folder above it that is not itself a `node_modules`. That covers nested (npm), hoisted (npm, the self-contained and managed installs) and pnpm's siblings. Its error names the launcher and, depending on where the lookup stopped, the script it runs or every folder tried; Providers shows it.

## RPC protocol

### Process and transport (`crates/pi-rpc/src/lib.rs`, `record.rs`)

`PiProcess::spawn(&spec)` launches the child with stdin/stdout/stderr on pipes and starts two threads:

- `pi-rpc-stdout`: reads records separated **by LF only** (`read_until(b'\n')`); Unicode separators (U+2028) are valid inside JSON strings. `parse_record` strips the trailing `\r` and classifies by `type`.
- `pi-rpc-stderr`: each line is `Incoming::Stderr`, never protocol data.

| stdout record | `Record` | Destination |
| --- | --- | --- |
| `type: "response"` with a pending `id` | `Response` | The waiting `request` |
| `type: "response"` with no owner and failed | `Response` | `Incoming::Stderr("<command> failed: …")` |
| `type: "extension_ui_request"` | `UiRequest` | `Incoming::Ui` |
| Any other `type` | `Event(Value)` | `Incoming::Event` (kept as JSON: Pi adds events over time) |
| Empty line | `Empty` | Ignored |
| Invalid JSON | — | `Incoming::Stderr("unparseable RPC record: …")` |

When stdout closes, pending requests are flushed (their callers get the error "gentle-shell exited before answering") and `Incoming::Exited(code)` arrives.

`request(command)` assigns `id` = `gs-<n>` and writes one line at once; the returned future holds only the response channel (`success: false` becomes `Err(error)`), so a pending request never keeps the process alive. `respond_ui(id, UiAnswer)` answers dialogs with `extension_ui_response` (`value`, `confirmed` or `cancelled: true`). `shutdown(grace)` is idempotent and returns at once: on Unix it sends SIGTERM to the launcher (forwarded to Pi, whose handler stops its agents' detached children; stdin stays open until then, because Pi drops that handler on stdin EOF), elsewhere it closes stdin; when the backend exits or after `grace`, it kills the backend's process group (Unix, spawned with `process_group(0)`) or tree (`taskkill /T /F`, Windows) and reaps it. `Drop` calls `shutdown(3 s)`; app quit calls it for every tab (`Workspace` `on_app_quit` → `SessionView::shutdown_backend`).

### Tab lifecycle (`features/session/lifecycle.rs`)

- `start` clears the tab state, resolves the `LaunchSpec` on the background executor, appends `--session <path>` if there is a conversation to resume (`backend.pending_session`), queries the version and calls `PiProcess::spawn`. Then `refresh_state`, the pending prompt (`-p`), and a loop that batches queued `Incoming` items (`drain_queued`) and applies them with `handle_batch` in a single update.
- Resuming happens at startup (`--session`), not with `switch_session` afterwards: Gentle Shell treats the startup session as new and starts it in the saved permission mode; a switched session starts in Normal.
- `restart_when_idle` / `backend.restart_pending`: restarts in the middle of a turn (or with a dialog open) wait for it to finish. Used by `reload` (`/reload`), `reload_models` (packages, the Claude bridge's plan, and a sign-in on a Shell without `reload_credentials`), `restart_for_update` (after `gentle-shell upgrade`) and `choose_mode` (permission change).
- `reload_credentials` (after a sign-in saved in the Providers screen): when the tab advertises `reload_credentials`, the tab sends it (a screen read, `state::desktop::reads`) instead of restarting: Gentle Shell refreshes its model registry offline, mid-turn too, and the tab re-reads `get_available_models`. An answer other than `reloaded: true, aborted: false` (a refusal, `reload_failed`, `auth_unavailable`, a timeout) falls back to `reload_models`; a backend replaced meanwhile read the credentials when it started.
- `retry_start` retries tabs whose backend never started (after onboarding).

### Permission mode (`state::desktop::permission`)

The picker's selection is the consent. When the backend's `capabilities` advertise `set_permission_mode`, the app sends `set_permission_mode` with `persist: true` over the Gentle Desktop RPC channel and switches the live session without writing `permission-mode.json` or restarting. The server's answer is the truth: `changed: false` is a no-op, a `persist_error` is live success plus a "default not saved" warning, and a timeout/transport/server failure reverts and reports. Events move the confirmed state only for the exact `permission_mode_changed` name that the capabilities `emits`; a sequence gap resyncs once through the channel's `get_snapshot`. The event's `source` is `desktop` (after a `set_permission_mode`) or, on Gentle Shell `main`, `external` (`/gentle:mode`, `/gentle:yolo` or the owner revoking YOLO, debounced); both move the confirmed state the same way.

Three cases keep the legacy path (save `permission-mode.json` and restart the backend on the same conversation, exactly once):

- Pi lists no `gentle:desktop` command (a Shell without Desktop RPC: `Permission::without_desktop`);
- the capabilities are known and do not list `set_permission_mode`;
- the server answers `unsupported_method` for the `set_permission_mode` it advertised.

While capabilities are still loading, a picker click reports "try again" and never writes the default file or restarts. `choose_mode` in `lifecycle.rs` is the only caller of either path; every other restart caller is unchanged.

The picker's live mode and default come from the permission slice (`get_permission_mode` seed, `set_permission_mode` answers, `permission_mode_changed`) as soon as it confirms them. `permission-mode.json` is read once when the tab is created, only as the default's placeholder until that seed answers, and stays the source on a Shell without Desktop RPC.

### Agents and jobs (`state::desktop::supervision`)

When the backend's `capabilities` advertise `list_subagents` and/or `list_jobs`, the app seeds a full list once the probe (capabilities → snapshot) and the permission seed have settled, then reconciles `agents_update`/`jobs_update` events by id. The structured lists are the primary source once seeded; the legacy `gentle-agents` widget and `details.gentleJobs` stay as the fallback for older Shells, and the panel/jobs chip never shows both, so the two sources cannot double a helper or a job. In-run progress (turns, tool calls and the step) has one source per helper (`gentle_core::activity::helper_progress`): on Gentle Shell 5.0.0 the projection carries `turns`, `toolCalls` and `activeTool` (progress throttled by the Shell to once per session per 500 ms, status changes at once), so the counts come from it and the step is `running <tool>` while a tool runs, else its closed step label; an older projection without them keeps the widget's counts and live step, as before. Time, label, prompt, error and the Activity thread still come from the `gentle-agents` widget's entry with the same task id (`Helper::Structured(agent, live)` in `session/agents.rs`), or `get_subagent_thread` for the thread; a structured helper the widget never published says so instead of showing a thread.

- `list_subagents` / `list_jobs`: empty params, answered with the typed `agents`/`jobs` arrays. Only these full-list responses mark a list as seeded. A list that cannot be decoded leaves the legacy fallback in place and is never retried in a loop; a malformed record never fabricates an empty list.
- `agents_update` / `jobs_update`: full bounded projections, so the event replaces the list (ids absent from the projection drop rather than growing forever). They never mark a list as seeded, so a pre-seed event is replaced by the real seed. A sequence gap forgets the seeded markers so the lists re-seed behind the channel's `get_snapshot` resync.
- `cancel_subagent` / `cancel_job`: params `{ id }`. One cancel in flight at a time, with the same timeout/rollback discipline as permission changes. The server's post-action projection is the truth: `cancel_subagent` answers `requested`/`changed` only when supplied (never defaulted, so an async cancel is not read as unchanged), and `cancel_job` answers `changed`. There is no job start method and no restart.

A new/open session (`new_session`/`switch_session`) resets the Desktop channel: it forgets the pending request and the event baseline without rewinding request ids and returns to Idle, so the following `refresh_state` re-probes capabilities and the supervision lists re-seed exactly once behind it. Late answers from the previous session are uncorrelated and benign.

The Agents panel's Stop button uses `cancel_subagent` when the peer offers it; a peer without the method (or a server `unsupported_method` answer) keeps the legacy "ask the agent to run `subagent_cancel`" prompt exactly once. Jobs cancel over `cancel_job` with no legacy prompt. Model, tokens and cost are shown per helper from the typed `usage` window, with an honest "unavailable" marker where the input/output/cache/reasoning breakdown is not recorded; prompt, tool output, paths and error text never cross the wire. The routed `model` is also shown on each helper's row in the Agents table, and with its `thinking` level in the helpers popover. The legacy `gentle-agents` widget carries no model, so on an older Shell no helper shows one.

### Subscription usage (`state::desktop::subscription`)

When the backend's `capabilities` advertise `get_subscription_usage`, the Usage screen reads the whole-account snapshot through this slice instead of `auth.json` and provider APIs, and its Refresh button re-reads with `refresh_subscription_usage`. The slice is pure RPC state: it never reads `auth.json`, resolves `$VAR`/`!command`, builds a bearer header, or calls ChatGPT/NaN. `rate_limit` events reconcile per-provider snapshots — Claude's 5h/week response headers included — so those windows finally arrive in the app.

- `get_subscription_usage` / `refresh_subscription_usage`: empty params for the whole account (or `{ provider }` for one). Both answer the same typed `providers` projection: `provider`, the closed `status` (`ok`/`pending`/`stale`/`failed`/`unavailable`), optional `fetchedAt`/`plan`/`refresh` (`unsupported`/`out_of_scope`), and `limits` → `windows`. No credential, account or URL field is part of the projection.
- `rate_limit`: `{ source: "refresh" | "response", snapshots }`. The snapshots are full provider projections, upserted by provider id; `source: response` is the per-turn response-header path (Claude), `source: refresh` the refresh path. The event only applies when the capabilities `emits` the exact name, and it never marks the seed fetched.
- One request in flight at a time, with the same timeout/rollback discipline as permission changes. A `pending`/`stale` entry with no limits keeps the last good limits (the data is still valid, just not fresh); `failed`/`unavailable` are shown honestly with no invented data.
- The legacy `auth.json` + provider API path runs only when the capabilities are known not to offer `get_subscription_usage`, or the server answers `unsupported_method` for a method it advertised. Any other RPC failure (timeout, transport, malformed, event gap) is shown honestly and never falls back to direct API calls. Without an agent tab, the screen keeps the legacy path.
- The composer's plan-limits chip reuses the same slice: it seeds `get_subscription_usage` once the session has a model, while it has nothing to show (outside the render pass, at most every 30 s; idempotent) and renders the provider matching the current model by alias (`codex`/`openai-codex`, `claude`/`anthropic`/`claude-bridge`, `openai`, `nan`; Gentle Shell files a bridged Claude turn under the provider that served it, so `claude-bridge` matches the same Claude plan). It never issues a refresh; the Usage screen owns that. On a legacy snapshot it hides while the per-turn limit chips would feed it — one number only — and when it does show, its card says "Plan limits need Gentle Shell 4.8.0 or newer".
- Per-turn limit notices (`notify`, "`N% used (window)`") stay a separate legacy chip path and never overwrite the structured provider windows.

### Design canvas (`state::desktop::design`)

When the backend's `capabilities` advertise `get_design_canvas`, the tab reads the canvas state once after the probe and follows the `design_canvas` events. Both become the same `SessionEvent::DesignCanvas(CanvasNotice)` the legacy paths produce, so the browser card and the stage list are unchanged. There is no open or stop method: the agent owns the canvas, the app only shows it.

- `get_design_canvas` is sent as `{ includeUrl: true }`: the interactive host is the client the server trusts with the tokenized URL. It answers `running`, `slug`, `connectedClients`, `designs` and, when asked, `url`. The seed goes out once per backend, after the channel is Ready and no other request is in flight; a backend reset or any event gap re-arms it. Every gap reaches the channel's `resync()`, whichever record showed it (channel, permission, supervision, subscription, design or config), so the canvas re-seeds exactly once behind the resync snapshot; while a deferred resync is owed, the seed waits for it, and settling the design request flushes that resync.
- `design_canvas`: `{ transition: "open" | "refresh" | "stop", ...state }`, applied only when the capabilities `emits` the exact name.
- Mapping: only an event closes the canvas: a `stop` event, or an event with `running: false`, → `Stopped`. The seed (and any re-seed after a gap or reset) never emits `Stopped`, because `Stopped` closes design cards another tab may own; a seed with `running: false` emits nothing. A running canvas with a loopback URL → `Open { url, refreshed }` (`refreshed` only for `refresh`; the seed is never a refresh). The slice remembers the URL it last opened (never printed; cleared by a stop or a backend reset): a seed with that same URL emits nothing, so a re-seed does not reload the page; an `open` event with it → `Reopen { url }`, since Gentle Shell sends `open` only while no page shows the canvas (a connected page gets `refresh`); `refresh` always reloads. Inside the app `Reopen` leaves the card as it is (as before); on **In my browser** it opens the canvas outside again. A running canvas without a URL navigates nowhere. The loopback check is the browser's canvas rule, read back exactly, plus `gentle_core::web::loopback_url` (which refuses a userinfo host such as `localhost:@host`). Any other URL is refused with a warning and nothing opens.
- The tokenized URL only travels inside the notice to the browser. Report messages, transcript notices and toasts from this slice never carry it, and its `Applied` type has no `Debug`.
- One request in flight, with the same timeout/rollback and generation discipline as the other slices; a late answer after a timeout or reset navigates nowhere. A peer without the method (or an `unsupported_method` answer) is silent and keeps the legacy path.
- Legacy paths stay for older Shells: the `notify` "Design canvas…" text and the `gentle_design` tool result. While the channel is Ready and the peer emits `design_canvas`, both are dropped so the canvas does not navigate twice: the `notify` text neither moves the canvas nor falls through to the loopback web opener, and the tool result emits no canvas notice. Otherwise both keep working as before.
- The system browser: Gentle Shell's `gentle_design open` launches it unless the backend starts with `GENTLE_DESIGN_OPEN_BROWSER=0` (gentle-shell#3517). Each agent tab sets it at launch (local, WSL and command backends alike) whenever the app shows the canvas itself from its URL (`gentle_core::web_browsers::design_launch_env`): with Configuration › Devices › Browser › Open pages on **Inside the app**, in its card in the instance tray; on **In my browser**, by opening it in the chosen browser (`Workspace::show_design_canvas`), so Gentle Shell's own system-browser tab would be a second one. Out there every new open opens a tab (`Open` that isn't a refresh, or `Reopen`), even at a URL opened before, because a new open means the earlier tab was closed; a refresh opens nothing; and the same URL again within 3 seconds is one open reported twice (an older Shell's `notify` text and `gentle_design` result; with `design_canvas` events the result is dropped anyway) and opens once (`gentle_core::web_browsers::OutsideCanvas`). The only case left unset is **Inside the app** on Linux under Wayland, where the card can't draw and nothing opens it outside, so the canvas stays in the tab Gentle Shell opens. The choice is read when the tab's backend starts, so a change applies to tabs started or restarted after it. With the variable, the canvas still starts and the `open` event (and the `gentle_design` result, `opened: false, browserDisabled: true`) still carries the URL the app opens. A Shell without the switch (5.0.0 and older) ignores it and opens its browser tab as well, as before; the app opens the canvas either way, since nothing here waits on the browser having opened.

### Config stores (`state::desktop::config`, `features/profiles/`)

When the backend's `capabilities` advertise both `get_config` and `set_config`, the Profiles screen reads and writes Gentle Shell's config stores through this slice, by store name: Desktop resolves no config path for them. The screen's stores are `profiles`, `profile_fallbacks`, `pins`, `models`, `subagents` and `managed_assets`; only the first three are ever written, and `models`, `subagents` and `managed_assets` are shown read-only (one summary line). The settings stores (`persona`, `banner`, `notifications`) are Configuration's (below): the screen ignores their `config_changed`.

- **Slice.** The screen holds tickets (`config_get`, `config_set` on the session). The slice queues them and sends one request at a time on the shared `DesktopSession`, once the channel is Ready, no resync is owed and no other slice has a request in flight; every Desktop record, timeout and disposition pumps the queue. Each ticket gets exactly one outcome: the decoded state, the failure, `Timeout`, or `Dropped` when the backend resets, the channel goes unavailable or a resync snapshot times out first. One request in flight, with the same generation/timeout/rollback discipline as the other slices; a late answer after a timeout or reset is benign.
- **Writes.** `set_config` always carries the `writeRevision` of its target as last read (from `get_config` or the previous `set_config` result), never a guess. Save, New, Duplicate, Rename and Delete are whole-store `profiles` replacements; a rename or delete follows `profile_fallbacks` (moved or cleared) and a rename follows the clone pin; "Use in this repo" sets or clears the `local` pin layer (`clear_pin`). "Publish to repo" sets or clears the `repo` pin layer (`{ source: "repo", profile }`, `profile: null` to unpublish), the same toggle `/gentle:profiles publish` makes, instead of sending that command as prompt text (the direct-file path keeps sending it); outside a Git worktree nothing is written. A rename only reports the committed declaration, as before. The pin labels the screen shows (`<Git common dir>/gentle-ai/profile-pin.json`, `.pi/gentle-ai/profile.json`) are names, not resolved paths; a declaration shadowed by a winning clone pin is not reported by the store, so the screen says so instead of showing none (and Publish then reads it as not declared: the Shell answers `changed: false` when it already is).
- **Missing store.** A missing `profiles` store is seeded with a `set_config` built from the `models` store's routing (the direct-file seed also folds in materialized agent routes; the RPC seed does not read agent files for it).
- **Failures.** `revision_conflict` re-reads that store once, shows a notice, recomputes the draft against the fresh store (unsaved edits are kept) and never retries or overwrites. `profile_apply_busy` (a profile apply started anywhere is still running) wrote nothing: the screen says so, keeps the unsaved edits, and never retries; save again once the apply finishes. `invalid_data`, `write_failed`, `config_unavailable`, timeouts and transport failures are reported and nothing is written to a file. Only `Unsupported` (capabilities without the methods) or an `unsupported_method` answer switch the screen to the direct-file code; any other failure never falls back.
- **Changes.** `config_changed` (applied only when the capabilities `emit` that exact name) re-reads the store it names unless its revision is already held (a write's own echo). The event is either `source: "desktop"` (after a `set_config`, with `writeTarget` and `writeRevision`) or, on Gentle Shell `main`, `source: "external"` (an editor, `/gentle:profiles`, the installer or another process; with the store's `status` and no write target): `ConfigChanged::origin` keeps them apart, and both re-read the store. Every event gap reaches the shared `resync()`, which also marks every store changed, so the screen re-reads them behind the resync snapshot.
- **Choosing the path.** No agent tab, a missing Desktop extension, capabilities without both methods, or a backend that failed or exited mean the direct-file path (there is no writer to race). While the probe has not answered the screen waits (15 s, then says so with Retry); a channel that failed while probing is reported instead of guessing a path.
- **Make default and Use in this session over `apply_profile`.** When the capabilities also advertise `apply_profile`, both buttons save the draft first (as before) and then send `apply_profile` with `mode: "default"` or `"session"`, so Gentle Shell runs its own `/gentle:profiles` action (routing, Pi's settings, the pin rule, the live orchestrator switch); Desktop writes no file and sends no `set_model` for them. A `confirmation_required` answer shows Gentle Shell's exact title and message in the screen's confirmation card; only the human's Apply resends the same request with `confirmation: token`, Cancel sends nothing, and a fresh confirmation is always shown again, never answered. `applied` shows the notes and re-reads `profiles`, `pins`, `models`, `subagents`, `managed_assets` and Pi's default; `not_applied` and every error (`unknown_profile`, `profile_apply_busy`, `profiles_unavailable`, timeouts) show the notes or the reason. From the request until its answer every store write is refused at `Remote::write` (as during Make default's files job) and the buttons are disabled. A `profile_applied` event (when advertised) re-reads the same stores, and an `applied` answer re-reads the tab's model and thinking level, which Gentle Shell may have switched. An `unsupported_method` answer to it is reported, never a switch to the files.
- **The session's profile.** Where the capabilities advertise `get_profile_binding` (Gentle Shell 5.0.0), the binding is Gentle Shell's own answer (`resolveSessionProfile`, the rule launches use): read once the probe lands, replaced by each `profile_binding_changed` event (a clear, the terminal's `/gentle:profiles`, a session-mode apply, a resume), and read again after `config_changed` on `pins` or `profiles`, a `profile_applied`, an applied `apply_profile` or an event gap, since a `follow`/`live` binding moves without a binding write. The screen marks the `explicit` binding (the one a clear undoes) as "Used in this session"; an `inherited`, `follow` or `live` profile is not shown as the session's own. Clear session binding sends `clear_profile_binding` where advertised (it takes Gentle Shell's profile apply slot, so `profile_apply_busy` is shown, never retried) and says whether Gentle Shell `cleared`, found it `unchanged`, or answered `not_cleared`. An older Shell keeps the previous behaviour: the tab remembers what it saw (an `applied` answer or `profile_applied` event in `session` mode, or the screen's own `set_model` switch), Clear session binding forgets it and sends `/gentle:profiles clear` as prompt text, and a binding made from the terminal or restored on resume is not seen. Either way a new or resumed session or a replaced backend starts unbound (`config::Config::reset`).
- **The agent list and Pi's default orchestrator.** Where the capabilities advertise `list_agent_definitions` (Gentle Shell 5.0.0), the screen reads them through it (`ReadRequest::AgentDefinitions`) on open and after a Shell apply: Pi's default is its `defaultOrchestrator` (only when `status: "set"`; `settings.json` is not read), and the agent names are its definitions. A Shell that lists every `/gentle:profiles` root (the built-in package agents with the `jd-judge-a`/`jd-judge-b`/`jd-fix-agent` core judges, the agent home, `~/.agents`, `<cwd>/.agents` and `<cwd>/.pi`, gentle-shell#3518) says where each agent came from (`source`: `builtin`, `user` or `project`); when every agent carries a known `source` (`AgentDefinitions::lists_every_root`), the answer is the whole list and no agent file is read. Decided per answer, never by version. Gentle Shell 5.0.0 sends no `source` and its read covers only `<agent home>/agents`, `<agent home>/subagents`, `<cwd>/.pi/agents` and `<cwd>/.pi/subagents`, so for such an answer (or an empty one, or one with a `source` this app doesn't know) the screen still reads the agent files of the roots it doesn't cover (`env::uncovered_agents`) and joins them by name (`files::reported_names`, `gentle_core::profiles::reported_assignment_names`: core agents first, the rest sorted). An older Shell, or a failed read, reads every agent file and `settings.json` as before.
- **The orchestrator mode.** Gentle Shell keeps each profile's mode (`organic` or `full-delegation`) in the top-level `workflow` map of `profiles.json`, not in the routing, and reads it for the profile in use on every prompt. The screen edits it in the draft like a route (header "Orchestrator: Organic / Full delegation"), Save writes it with the routing, and Rename, Duplicate and Delete carry it (`gentle_core::profiles::set_orchestrator_mode`). Only non-default modes are written; entries that name no profile or no known mode are dropped and said, as Gentle Shell does. Applying the profile (Use in this session, Make default) needs nothing more: Gentle Shell picks the mode up from the profile.
- **Make default on files (older Shells).** Without `apply_profile` there is no server method that materializes routing (`models.json`, agent frontmatter, `subagents.json`, the managed-assets manifest) or Pi's `settings.json`, so Make default keeps the guarded multi-file flow in `profiles/apply.rs`, including its own `profiles.json` active-marker write. On the RPC path it is kept from racing the Shell's writer in both directions (`files::files_job_start`, `env::Remote`):
  - *RPC write → Make default.* It starts only when no store write is open and no read of the `profiles` store is open or owed, and the `profiles.json` it rewrites is built from the store as last read, never from an older copy. Otherwise it refuses with a notice and writes nothing.
  - *Make default → RPC write.* From that start until its background job finishes, every store write (Save, New, Duplicate, Rename, Delete, the fallbacks follow, pin set/clear) is refused at `Remote::write` with "wait for Make default to finish" and never sent; nothing is adopted, so the unsaved draft stays and can be saved afterwards. The buttons are also disabled while the job runs.
  - Together these mean no RPC write can land between Make default's start and its file write, so it never writes `profiles.json` from a stale copy. When it finishes, the hold is released and `profiles`, `pins`, `models`, `subagents` and `managed_assets` are re-read through the Shell, so the next RPC write is guarded by the revisions Make default left (a write sent before that re-read lands can only conflict, never overwrite). A re-read asked for while a read of the same store is open does not run alongside it: the store is marked dirty and exactly one more read follows the open one, so the shown state is never older than the request. The agent list and Pi's default orchestrator are not config stores: see above for where they come from.

### Screen reads (`state::desktop::reads`, `session/reads.rs`)

Window screens ask a tab's Gentle Shell instead of reading files or the network, each only when that tab's `capabilities` advertise the method; every other Shell (4.8.0 included) keeps the screen's own path, unchanged, and is never sent one.

- **Which tab.** The window's active agent tab, as the other screens pick it (`Workspace::active_session`): the agent pane focused in the active tab, else the first agent pane of that tab, else the first agent pane of the workspace. Opening the screen starts that tab's backend if needed. No agent tab is the screen's own path.
- **Deciding.** `SessionView::read_support(method)`: `Rpc` when the method is advertised; `Legacy` when it is not, the backend failed or exited, the extension is missing or the channel stopped; `NotReady` while the probe runs (or the backend starts). Sessions and Local stats wait for a `NotReady` tab at most `READ_DECIDE_WAIT` (3 s), then take their own path; Configuration takes the npm path at once, and asks `get_status` once the tab decides.
- **Slice.** `SessionView::read(ReadRequest)` returns a ticket; the slice queues reads behind the config queue and sends one at a time on the shared `DesktopSession` once the channel is Ready and no resync is owed. Each ticket gets exactly one `ReadOutcome` (the typed answer or a `ReadFailure`: `Unsupported`, `Refused { code, message }`, `Timeout`, `Dropped`), taken by the screen that holds it (`take_read`), which observes the tab. These reads wait 30 s (a listing or stats scan reads every session file in scope, a switch replaces the session, an update refresh is bounded by the Shell's 15 s, a status read audits every managed asset file); the other Desktop requests keep 10 s. A `session_switching` answer did nothing, so the read is queued again 300 ms later, at most three times.
- **`switch_session`.** An answer with `changed: true` means the session was replaced under the tab, exactly as after Pi's own `switch_session`: the tab forgets the conversation, re-probes the channel (its `seq` restarted at 1) and re-reads `get_state` (so `sessionFile` and resume-on-restart follow), the messages and the rest.
- **Sessions browser** (`features/sessions/view.rs`). Used when the tab advertises both `list_sessions` and `switch_session` and runs in the folder browsed. It lists 50 per page newest first (`scope` from the This project / All toggle; **Load older sessions** sends `nextCursor`), filters the loaded pages by name, first message or project, and opens a session with `switch_session { id }` in that tab (`scope` omitted for This project). In All, a session whose `project` is another folder's name opens in a new tab rooted at its folder, as before: the listing carries no path, so `discovery::find_session` finds that one file by id (file name first, then headers). One whose `project` matches is switched with `scope: "project"` first; `not_found` there means another folder with the same name, which opens in a new tab the same way. `cancelled` keeps the tab's session and says so; `sessions_unavailable` shows the Shell's message. A page that fails (`sessions_unavailable` for an in-memory session, a timeout…) hands the list to the session files.
- **Local stats** (`features/usage/shell_stats.rs`). `get_usage_stats { range, scope: "all" }` per range (7 days, 30 days, all time; answers are kept per range until refresh), mapped onto the tab's summary: totals, models (no provider chip: the answer names none), projects by display name, active days (days with usage), and a chart of the range's days up to 30. From Gentle Shell 5.0.0 each `byDay` row carries its `cost` and the answer lists `byProvider`: the chart then offers Tokens / Cost as on the file scan, and a Providers table (messages, tokens, cost, share) appears under Models. An older Shell's answer has neither (detected by their absence, not by capabilities: the method is the same), so its chart stays tokens only and no Providers table shows. Rows the Shell left out are noted (`truncated`, providers included). Any failure, `stats_unavailable` included, falls back to the session file scan.
- **Gentle Shell status** (`settings/shell_status.rs`). Opening Configuration (and its reload button) reads `get_status {}` when the active agent tab advertises it; once its tab is ready if it was still starting. General › Gentle Shell then shows the severity as a chip ("OK", or "Needs attention" with a pointer to `/gentle:doctor`) and one row each for the persona in effect, the `gentle-ai` dev-binary override (with its SHA-256 prefix while active), the delegation and review assets (stale, replaced by the user, shadowed by active agents; stale ones name `/gentle:install-<owner> --force`) and the model configuration (`models.json` present, routing valid/invalid/not saved). `status_unavailable` or any failure shows nothing; a Shell without the method shows the section as before.
- **Update status** (`settings/upgrade.rs`, `features/updates/status.rs`). Opening Configuration reads `get_update_status {}`; when nothing backs that answer (`gentleShell.checkedAt` null, not offline) it asks once more with `refresh: true`, as the npm path would on a stale cache, and the header's reload button always refreshes. The "Gentle Shell X is available" card comes from it for a `release` or `bundled` channel with a newer stable release (`offer_for`, so "Skip this version" still hides it), never for `gentle-ai-managed` or a launcher the app sees as managed. On unmanaged installs, a newer `main` commit gets **Update now** (`gentle-shell upgrade --channel main`), and a newer Pi gets **Update Pi** (`gentle-shell update`, then refreshes the answer). The app runs these commands only when their buttons are clicked. The Gentle Shell and Engram card always shows rows for the channel, Gentle Shell's state (up to date, a newer release or `main` commit, or why it was not checked: never "up to date" for `unknown`), the update command as reported by the Shell, Pi's state (its latest version only when the Shell names it, today bundled installs), and the last check time, plus a **Check for updates** button that reads with `refresh: true`. Packages Pi's check found newer get an **update** chip in Packages (**update → X** when the Shell names a version; today it never does), pinned ones **pinned**, skipped or unknown ones **not checked**, and `no_update_reported` none, with a line saying Pi's check reported no updates (not that they are up to date) and an **Update packages** button (`gentle-shell update --extensions`, which refreshes the answer when it finishes; hidden for a managed install). A failed read falls back to the npm path until Configuration opens again.
- **Background subagents** (`settings/background.rs`). Opening Configuration reads `get_background_subagents {}` (a tab still probing is asked once its probe answers); the Gentle AI row then shows the answer (`BackgroundPolicy::from_shell`: the same sources and the fail-closed `malformed`; the project file keeps the name the files' read gives it, as no path crosses the wire). A read that fails keeps the files' read. The Off/On switch sends `set_background_subagents { policy }`, which writes nothing: Gentle Shell's confirmation (its title and message exactly as sent, including when this project's file decides instead) is shown under the switch; **Turn on/off** resends the same request with `confirmationToken`, Cancel sends nothing, and a stale token is answered with a fresh confirmation that replaces the shown one. `applied` shows the re-read state. `background_subagents_busy` is queued again like `session_switching`; other failures are said and the policy re-read. A Shell without the methods (4.9.0) keeps the files' read and the `/gentle:background-subagents enable|disable` command, unchanged.
- **Sign-ins** (`settings/sign_ins.rs`, `onboarding/checks.rs`). Opening Configuration reads `get_auth_status {}`: Models › Sign-ins lists the providers with credentials and their kind (`oauth`, `api_key`), from Pi's registry in memory (stored sign-ins, environment, `models.json`, extensions; never a value), instead of the keys of `auth.json`; and the embedded Setup & requirements provider check follows it (`gentle_core::setup::registry_sign_in`, `checks::with_registry`, kept over later looks). A failed read keeps the file reads. The onboarding screen and the welcome sequence, which have no tab to ask, keep reading `auth.json`, `models.json` and the environment (`setup/extras.rs`, `setup/remote.rs`); sign-in itself stays with the login helper.
- **Profiles' agent list and Pi default** (`features/profiles/mod.rs`). Once the screen is on the RPC config path, `list_agent_definitions` replaces the agent-file discovery (all of it when its agents carry `source`, else for the roots it covers) and Pi's `settings.json` read (see Config stores); a refusal or failure reads the files instead.

### Review mode (`state::desktop::review`, `session/view/review.rs`)

When the backend's `capabilities` advertise both `get_review_mode` and `set_review_mode` (Gentle Shell `main`), a chip beside the permission chip shows the receipt-driven development switch: "Review on", "Review off" (warning color) or "Review ?" (the read failed; nothing is assumed). Its card says what decides it now (the default, this repository's setting, or the machine-wide one, which wins) and has one row per setting, "This repository" (`scope: clone`) and "All repositories" (`scope: global`), each with the change it offers: this repository's row flips what applies here; the machine-wide row turns back on only an explicit machine-wide off.

- **Reads.** `get_review_mode` once the probe lands, again when the card opens (a change made in the TUI, Herdr or another process emits nothing), after a sequence gap and after a change whose outcome is unknown. `review_unavailable` on a read (no `gentle-ai`) or `unsupported_method` hides the chip silently. `review_mode_changed` (only the exact advertised name) moves it.
- **Changes.** A row sends `set_review_mode { enabled, scope }`, which writes nothing: the server answers a confirmation, shown over the composer with its title and message exactly as sent. Approve resends the same request with `confirmationToken`; Cancel sends nothing. A stale token (the switch moved meanwhile) is answered with a fresh confirmation, which replaces the one shown; only the human's approval ever sends its token. `applied` shows the re-read mode as the server reports it (`gentle-ai` refuses to clear a repository's off while the machine-wide one is off: the chip then keeps showing off). `review_mode_busy` and `review_unavailable` on a change are reported in the conversation; the latter re-reads the switch, nothing is retried.
- **Slice.** One request at a time on the shared `DesktopSession` once the channel is Ready and no resync is owed (the user's change first, then a read), with the same generation/timeout/rollback discipline as the other slices. 4.8.0 lacks both methods: no chip, nothing sent.

### Settings stores (`settings/shell_config.rs`)

Configuration shows the persona (Agents › Gentle AI), the terminal banner (Appearance) and the notification policy (Notifications) from Gentle Shell's own stores when the active agent tab's Shell serves them, and keeps the files as the fallback:

- **Choosing the path.** Opening Configuration (and its reload) sends `get_config` for `persona`, `banner` and `notifications` through the config slice when the tab advertises `get_config` and `set_config`; a tab still probing is asked once its probe answers. The methods are older than the stores, so the gate is the answer: `unknown_store` (Gentle Shell 4.9.0 and older know six stores), `unsupported_method` or capabilities without the methods put that store back on its file for as long as the screen is open, exactly as before. Any other read failure keeps what the files showed.
- **Reads.** `persona` is the mode in effect (the project layer wins, as Gentle Shell resolves it); `missing` shows the default. `banner` is described like `banner.json` (`describe_banner`). `notifications` becomes a `gentle_core::notifications::Policy` (`Policy::from_store`): `missing` and `invalid` are the default preset, as with the file, and a file sound arrives as the `"file"` marker.
- **Writes.** The notification switches send the whole store (`Policy::store_data`: the settings without `schema`) with `set_config`, guarded by the `global` target's `writeRevision`; a file sound is sent back as the marker, which keeps that file. One write at a time; nothing is written to `notifications.json` on this path. `revision_conflict` re-reads the store and says to choose again; other failures are said and nothing is retried. The persona and the banner stay read-only here, as before.
- **Changes.** `config_changed` for a store shown from the Shell re-reads it unless its revision is already held (the write's own echo); a gap re-reads all three.
- **Playing.** The app plays alert sounds itself (`features/alerts`), and a sound file's path never crosses the wire, so playback keeps reading `notifications.json`. The session hero's banner (`shared/banner.rs`) is drawn before the tab's backend answers and keeps reading `banner.json`.

### External config and permission changes (Gentle Shell #3335)

On Gentle Shell `main`, a change made outside Desktop arrives on the channel: `config_changed { source: "external" }` (an editor, `/gentle:profiles`, the installer, another process; no write target) and `permission_mode_changed { source: "external" }` (`/gentle:mode`, `/gentle:yolo`). Both go through the same slices as Desktop's own events: the Profiles screen re-reads the named store (`config_external_change_is_a_store_change_the_screen_rereads`, `rpc_config_changes_reread_only_what_moved`) and the permission chip follows the confirmed mode (`permission_external_event_moves_the_chip_like_a_desktop_one`). The app never polled these files, so there is no polling to retire: the Profiles screen reads on open and on `config_changed`, the chip reads `permission-mode.json` once at tab creation as a placeholder. On 4.8.0 an external edit shows the next time Profiles opens, as before.

## Devices: Android emulators and iOS simulators

Configuration → Devices has two switches, saved in the app's `settings.json` under `devices` (`enabled`, `agents`):

- **Use devices** installs Expo's device hub (`expo-device-hub` 0.22.1, the version T3 Code pins: serve-sim for iOS, serve-emu for Android) with npm into `toolchain/devices/expo-device-hub-0.22.1`, and shows the device panel's button in the title bar.
- **Agents can use devices** installs Callstack's `agent-device` 0.21.36 the same way (its `node_modules/.bin` joins the agents' PATH) and adds the device instructions to new agent sessions.

Both need Node 22.12 or newer. iOS streaming needs Apple silicon and Xcode (`simctl`); Android needs the SDK, and emulator video needs `ffmpeg` with libx264 (the section offers the install command in a terminal tab). All of this is `setup/devices.rs`.

### The hub (`features/devices/hub.rs`)

One process per app, started on first use (the panel shows, or `gentle-device` asks): `node <entry> --port <free port> --host 127.0.0.1 --hide-sidebar --hide-boot-device`, plus `--platform android` off Apple-silicon macOS, with `ANDROID_HOME` and `DEVELOPER_DIR` (when `xcode-select` points at the Command Line Tools) set, output in `<data>/gentle-shell-gpui/devices/hub.log`. Ready when `GET /readyz` answers; its port and pid go in `devices/hub.json` for `gentle-device`. It stops with SIGTERM (helpers first) when "Use devices" goes off or the app quits; devices the app booted are shut down first.

API used: `GET /api/devices` (`gentle_core::devices::hub_devices` reads it and adds AVDs from `emulator -list-avds` the hub doesn't list yet), `POST /api/devices/boot` and `/api/devices/shutdown` with `{platform, id, name}`; booting is headless (no Simulator.app, no emulator window). The list is polled every 3 s while a panel shows and every second while a device boots; not at all otherwise.

### The panel (`features/devices/panel.rs`)

One `DevicePanel` per window: a tab per device, docked as a 400 px column at the right of the panes (default) or floating as a card (`shared/floating.rs`); a header button switches. Each tab is the hub's own viewer page (`/`, live stream with touch, keyboard and hardware buttons) in a `browser::WebSurface`, pinned to its device by an initialization script that sets `window.__EXPO_DEVICE_HUB_SINGLE_DEVICE__` (what the hub's `--single-device` does). Only the active tab has a web view; hiding the panel drops it, and a screen over the window hides it. The + button lists every device (running first) and opens one, booting it when it's off. ⌘K → Devices shows the panel.

### Agents

- **`gentle-device`** (`devices/cli.rs`): a shim in `toolchain/bin` that runs the app binary with `--device`. `list` asks the app to start the hub (`OpenRequest.device`, through the single-instance server; the window doesn't come forward), waits for `hub.json` and prints the list. `open <name|id>` asks the app to open the device (it boots it and shows its tab), waits until it runs and prints `agent-device --platform ios --udid <id> …` / `--platform android --serial <serial> …` calls. `close <name|id> [--shutdown]` closes the tab (and turns it off).
- **Instructions** (`devices/instructions.rs`): `<data>/gentle-shell-gpui/agent-instructions.md`, appended to every new RPC session's system prompt with `--append-system-prompt <file>` (`pi_rpc::set_system_prompt`; a file because Windows' `.cmd` launcher mangles quotes and newlines in arguments). Pages always: `gentle-open <url>`, never an outside browser. With both switches on, devices too: `gentle-device` to open, `agent-device` for every launch, tap, text and screenshot, never `simctl boot`, `open -a Simulator`, `emulator -avd` or `adb shell input`.
- **Commands agents run anyway**: `SessionView` reads each `bash`/`bash_background`/`monitor` command. `gentle_core::devices::launch_intent` recognizes `emulator -avd <name>`, `emulator @<name>`, `[xcrun] simctl boot …` and the Windows forms (`start "" …emulator.exe`, `cmd /c start`, `Start-Process emulator -ArgumentList …`); the panel then opens that device's tab once it runs (for 3 minutes). `device_command` names the last `adb`/`simctl`/`maestro`/… command, shown under the tabs.

The Android SDK's `emulator` and `platform-tools` are on the agents' PATH (`devices::android_tool_dirs`): Android Studio doesn't put them there.

## Generative UI: `gentle_ui`

The agent shows interactive surfaces in the conversation: diagrams (architecture, data flow, dependencies), the native kinds below (tables, forms, checklists, kanban boards, charts), change reviews, the canvas kinds (sequence diagrams, data models, state machines, timelines) and html pages run as MCP Apps; the user edits or uses them natively and what they do goes back to the agent. The protocol is a Pi extension the app ships, `features/genui/gentle-ui.ts`, embedded with `include_str!`.

- **Installation** (`genui/extension.rs` `install`): at startup the app writes it to `<data>/gentle-shell-gpui/extensions/gentle-ui.ts` (only when the content differs) and `main.rs` passes the path to `pi_rpc::set_extensions`, so every new RPC session starts with `--extension <file>`. The gentle-shell launcher doesn't parse `--extension`: `parseLauncherArgs` puts unknown arguments in `passthrough` and `buildPiInvocation` appends them after its own `-e` injection, so Pi loads it in every home mode (a take-over's `--no-extensions` still loads explicit `-e`/`--extension` paths). It imports only host-provided modules (`@earendil-works/pi-coding-agent` types, `typebox`, `@earendil-works/pi-ai`); no `npm install`.
- **Tool `gentle_ui`** (`executionMode: "sequential"`): `{ action: "show" | "update" | "close", id?, title?, kind?: "diagram" | "table" | "form" | "checklist" | "kanban" | "chart" | "html" | "review" | "sequence" | "erd" | "state" | "timeline", spec?, patch?, wait? }`. `show` takes a full spec and uses `id` when it is a free slug (`^[a-z0-9][a-z0-9-_]{0,63}$`), else `ui-<n>` (1 + the highest number seen on the branch); version 1, kind `diagram` and the kind's name as title (`Diagram`, `Table`, `Form`, `Checklist`, `Board`, `Chart`, `HTML`, `Review`, `Sequence`, `Data model`, `State machine`, `Timeline`) by default. `update` takes `spec` (replace) and/or `patch` (merge, an object); an id keeps its kind (an update naming another kind is an error). A diagram's patch upserts `nodes`/`groups` by id and `edges` by id or `from`+`to`, `null` clears a field, `remove: { nodes, edges, groups }` with a removed node's edges and a removed group's memberships going too, `direction`; the other kinds' patches are below. Version + 1. `close` forgets the id. `wait: true` (review only) keeps the call open until the user's decisions arrive (see `kind: "review"`). Invalid input throws a readable error (at most 10 problems) that the model sees as a tool error. Each kind is one `KINDS` entry in the extension (`{ noun, title, normalize, patch, summary, instructions? }`).
- **When the agent uses it: Agent UI** (Configuration → Agent UI; `gentle_core::genui::mode::Mode`, `features/genui/mode.rs`, `settings/agent_ui.rs`): `Proactive` (default), `When asked` or `Off`, saved in the app's `settings.json` as `genuiMode` (`"proactive" | "asked" | "off"`; anything else reads as proactive). The tool's rules are a mode policy followed by mode-neutral how-to bullets (`GUIDELINES`: picking the kind, updates, refs, events, examples, run plans, boards, live data, review and html protocols). **Proactive** puts two bullets first: use `gentle_ui` unprompted when a surface clearly beats prose (a system with 4+ interacting parts explained or proposed → diagram with refs; calls over time → sequence; a schema or migration → erd; a workflow or lifecycle → state; dated work with dependencies → timeline; a plan of 4+ steps or work about to be executed → checklist with `run: true`; 3+ options on 2+ attributes → table; 2+ decisions needed at once → one form; numbers over time or by category → chart; multi-file or risky edits → review first), and the anti-triggers (not for simple answers, one-liners, small edits, text-only requests or decoration; update an open surface for the same thing instead of showing another; at most one new surface per reply unless asked; short prose around it). **When asked** puts one bullet first: only when the user asks for one (or to update one already open), otherwise text. **Off** deactivates the tool (`pi.setActiveTools` without it, so its declaration and rules leave the prompt; registered with `defaultActive: false` when launched off), adds one rule (`promptGuidelines`: Agent UI is off, answer in text, earlier surfaces are read-only), rejects a call already on its way with an error naming the setting, and appends that note to `gentle-ui.event` messages (user edits and inserted templates), since the agent can't update them. Off keeps the user's side: surfaces already in conversations, their editing and sending, and `/ui-template` (inserting is the user's act; the agent is told it can't update it). Delivery: each agent tab launches with `GENTLE_UI_MODE=<id>` (`session/lifecycle.rs`); a change sets a GPUI global that every `SessionView` observes (`genui::mode::follow`), and a tab whose backend has another mode runs `/gentle-ui:event {"op":"mode","mode":"<id>"}` (`SessionView::sync_genui_mode`; a tab still starting gets it once ready). The extension takes the mode (not answered through the outcome widget; an unknown mode is a notify error), writes it to `process.env.GENTLE_UI_MODE` so a reload (new, resumed or forked session) starts in it, and syncs the tool's activation. Per run, a `before_agent_start` handler sets `systemPromptOptions.toolGuidelines.gentle_ui` to the mode's rules (or pushes the Off rule): Pi rebuilds the options from the registered tools every run and patches only changed sections, so an unchanged mode costs nothing and a change patches the rules once.
- **Spec** (`kind: "diagram"`): `{ direction: LR | TB, groups: [{id, label, description?}], nodes: [{id, label, kind, group?, description?, tech?, status?, x?, y?}], edges: [{id, from, to, label?, style}] }`, stored normalized: unknown node kinds become `service`, unknown edge styles `sync`, unknown statuses are dropped, `x`/`y` only as a pair (rounded), missing edge ids become `<from>-><to>` (`#2`, `#3`… when taken), long text is cut with `…` (label and tech 80, description 1000). Hard errors: missing `nodes` array (or `groups`/`edges` that aren't arrays), nodes without id, ids over 64 characters, duplicate ids, edges to unknown nodes, groups not in `groups`, more than 200 nodes, 400 edges or 50 groups. `gentle_core::genui::diagram` applies the same rules.
- **Result**: `content` is a compact summary the model reads (counts, groups, nodes with kind/group/status, edges with label/style; 60 entries per list at most); `details` is `{ id, version, kind, title, spec }` with the full normalized spec, or `{ …, spec: null, closed: true }` on close.
- **User edits**: the app sends the prompt `/gentle-ui:event {"id","version","changes","summary","spec","note"?}` (one line, `gentle_core::genui::event_command`; `version` is the one the user edited, `changes` and `summary` come from `genui::changes::summarize`). The command (`gentle-ui:event`, hidden by `gentle_core::commands::hidden`) adopts `spec` as authoritative with version + 1 and calls `pi.sendMessage({ customType: "gentle-ui.event", display: true, content, details })`; `details` is `{ id, version, kind, title, spec, changes, summary, note, baseVersion }`, `content` lists the summary lines, the note, the changes as JSON and the new summary. Delivery: idle → `triggerTurn: true` (a new turn answers the edit); mid-turn → `deliverAs: "steer"` (after the current tool calls, before the next model call). Unreadable JSON only answers with an error `notify`; everything else answers with an outcome (below).
- **State**: nothing is stored outside the session. On `session_start` and `session_tree` the extension walks `sessionManager.getBranch()`: `gentle_ui` tool results and `gentle-ui.event` custom messages with `details.id` set or close the surfaces; later entries win. The app rebuilds the same state from the transcript (tool items and custom messages).
- **In the app** (`features/genui/`): `GenUi::sync` runs from `SessionView::sync_view` whenever a changed transcript item is a `gentle_ui` tool item or a `gentle-ui.event` message (or the transcript was replaced: `get_messages`, a new or opened session), and keeps one `Surface` per id (`Diagram(DiagramView)`, `Panel(PanelView)` or `Html(HtmlView)`; an id shown again as another kind gets a new one). Its live card is drawn at the id's latest tool item; earlier tool items show as superseded rows, a running call as "Drawing…" and a failed one with the extension's error. A newer version replaces the view's base and replays the user's unsent edits on top; the viewport stays unless the user never moved it. Edits are `genui::changes::apply` on a local copy (undo keeps 100 steps), counted against the base in the footer, and Send runs `run_extension_command` with the command line above; Expand shows the same view in place of the conversation (the composer stays), and "Ask about this" puts a reference to the selection in the composer.
- **Outcome of an event** (every kind): the extension answers every `/gentle-ui:event` with `ctx.ui.setWidget("gentle-ui.outcome", [json])` then clears the key (`setWidget(key, undefined)`); `json` is `{ id, version, ok: true, current }` (`current` the surface's version now) or `{ id, version, ok: false, error }` for an unknown id, a `version` that is no longer the current one (the agent updated the surface meanwhile; not checked for html, whose events don't edit the spec) or an invalid spec. The handler runs before Pi answers the prompt, so the outcome arrives first. `session/events.rs` routes that key to `GenUi::outcome` (parsed by `gentle_core::genui::outcome`), never to the widget chips, and `Surface::outcome` hands it to the view of that id, which ignores an answer about another version. Every view stays "Sending" (`diagram::SendState`) until then: a diagram's or panel's accepted edits become its base and version (edits made since stay pending; panels through `Edits::mark_sent`/`accept_sent`), rejected ones stay pending with the reason in the footer and Retry/Discard; an html page's message is answered to the page only when accepted, and a rejected one waits for Retry or Discard (which tells the page it didn't go). A `handled` answer with no outcome (an extension from before outcomes) still counts as sent, as does the echo of exactly the sent spec.
- **Edits the card makes** (`genui::changes`, wire `op`s): `move`, `update_node` (label, kind, group, description, tech, status), `add_node`, `remove_node`, `add_edge`, `update_edge` (label, style), `remove_edge`, `add_group`, `update_group` (label, description), `remove_group` (its members become ungrouped) and `set_direction`. Dropping a dragged node into another group's box (as it was before the drag) or out of its own moves it between groups (`changes::group_on_drop`).
- **Layout** (`genui::layout`): layered (Sugiyama-style): cycles broken by reversing back edges, longest-path ranks, one band per group ordered by connectivity (ungrouped first), dummy nodes for edges spanning several ranks, alternating barycenter sweeps with adjacent swaps keeping the ordering with the fewest crossings, and edges routed as smooth Bézier chains through their dummies, around the boxes. Pinned nodes (`x`/`y`) keep their place and never move the others.
- **Limits**: `tool_execution_start` carries the final arguments and the result follows at once, so there is no streaming preview of a diagram being written.

### Native kinds: table, form, checklist, kanban, chart

`GenUi` keeps a `Surface::Panel(PanelView)` (`features/genui/panel.rs`) for these kinds. Each kind's spec is parsed and validated by `gentle_core::genui::<kind>` with the same defaults and hard errors as the extension's `normalize<Kind>`; edits go through `genui::edits::Edits` (base + working copy, undo 100, `rebase` replays unsent edits on a newer version, `summarize` gives the change JSON and one sentence each, `mark_sent`/`accept_sent` adopt what the extension took) and are sent with `genui::event_command_json` in the same `/gentle-ui:event` envelope, answered like the diagram's (see Outcome above).

- **table**: `{ columns: [{key, label?, type?: text|number|date|status|link, align?: left|center|right}], rows: [{id, cells: {key: value} | [values…]}], sort?: {column, direction: asc|desc}, selectable? (true), editable? (false), selection?: [row ids] }` (columns may be plain strings; a row's own keys count as cells; missing row ids become `row-<n>`; link cells are a URL or `{text, url}`). At most 30 columns, 500 rows, 500 characters per cell. Patch: `rows` upsert by id (cells merge, `null` clears), `columns` by key, `remove: {rows, columns}`, `sort`, `selection`, `editable`, `selectable`. Changes: `{op: "edit_cell", row, column, value}`, `{op: "select", rows}`. Sorting and the filter field only change the view.
- **form**: `{ fields: [{id, type: text|textarea|number|select|multiselect|checkbox|radio|slider|date, label, help?, placeholder?, required?, options?: [value | {value, label}], min?, max?, step?, default?}], description?, submitLabel?, values?, submitted? }` (`min`/`max`: number bounds, text length, multiselect count, ISO dates for dates; sliders default to 0–100; invalid defaults are dropped). At most 50 fields, 50 options. Patch: `fields` upsert by id, `values`, `remove: {fields}`, `description`, `submitLabel`; any update reopens a submitted form unless it sets `submitted: true`. Change: one `{op: "submit", values}` with every answer, validated in the app first (`Form::validate`); the form then shows read-only.
- **checklist**: `{ items: [{id, label, done?, note?, items?: [sub-items, one level]}] }` (items may be plain strings; missing ids are slugs of the label). At most 200 items. Patch: `items` upsert by id at either level (`parent: id | null` places or moves one), `remove: {items}`. Changes: `toggle`, `edit` (label, note), `add` (appended under `parent`), `remove`, `order {parent, items}` (a list's new order, pulling items from elsewhere: moves, indents and reorders).
- **kanban**: `{ columns: [{id, label, limit?}], cards: [{id, title, column, description?, tags?, assignee?}] }` (columns may be plain labels; a card without column goes to the first; cards are kept grouped by column). At most 12 columns, 300 cards, 8 tags. Patch: `cards`/`columns` upsert by id, `remove: {cards, columns}` (a removed column's cards go too). Changes: `add_card`, `update_card`, `remove_card`, `order {column, cards}` (moves between and within columns).
- **chart**: `{ type: bar|line|area|pie|donut|scatter, labels?, series: [{name, values}] (scatter: points: [[x, y]] or [{x, y}]), xTitle?, yTitle?, unit?, stacked? }` (one value per label; missing labels are 1…n; pie/donut values ≥ 0; `stacked` only for bar and area). At most 12 series, 1000 points. Patch: `series` upsert by name, `remove: {series}`, top-level keys replace. Read-only: no changes; hover shows a value, a click selects it for "Ask about this". `genui::chart` lays it out (round axes, bars, points, slices) and hit-tests.
- **Summaries** the model reads: counts, the columns and up to 30 rows; the fields and the prefilled or submitted answers; every item as `[x]`/`[ ]` lines; each column's cards; each series' values. Tool guidelines (`promptGuidelines`) say when to use each kind and carry one small example each.
- **Motion** (`genui/motion.rs`, shared with the diagram's tweens, view easing and marching edges): charts grow in and tween to a new version (300 ms ease-out), rows and cards glide to new places with `ui::spring`, new ones fade in, a check pops; only while something moves, with the window active, and never with reduced motion or backdrop motion Still (`motion::may_move`).

### Code refs, pinning, export and templates (every kind)

- **Code refs** (`gentle_core::genui::refs::CodeRef`): diagram nodes, erd tables, table rows, checklist items (and sub-items) and kanban cards take an optional `ref: {path, line?, endLine?}` (or the shorthand `"path:line"` / `"path:line-end"`), stored as `{path, line?, endLine?}` with `/` separators and `.`/`..` folded. A relative path climbing out of the root is a hard error (`node "api": ref path "../x" escapes the workspace`) in the app and in the extension (`normalizeRef`), which also turns absolute paths inside its `ctx.cwd` into relative ones and rejects absolute paths outside it. The tool guidelines ask the agent to attach a `ref` whenever an item corresponds to code (with an example). In the app (`genui/refs.rs`) a ref is a `FileCode` + `file.rs:42` link (`ui::mono()` 11 px in `accent`; `FileX` in `faint` when the file isn't in the workspace, checked at most every 5 s): on checklist rows, kanban cards and their details, a table's Code column, a diagram node's top-right corner, an erd table's header (both icon buttons) and their details. A click emits `DiagramEvent::OpenRef`; the conversation resolves it against its cwd (`CodeRef::resolve`, lexical, inside the root only) and the window opens it in the file viewer at the line (`SessionEvent::OpenFile` → `Workspace::open_file_at` → `FileView::go_to_line`). Right-click: Open in the file viewer, Open in <editor> for each installed editor (`platform::ides::open_file`; VS Code and its forks at the line through `<scheme>://file/…:line` on macOS and `--goto` elsewhere, Zed and Sublime Text with `path:line`; `gentle_core::ides::launch_file`), Copy path.
- **Pinning** (`genui/pinned.rs`, `GenUi::pin`): the Pin tool in every surface's header (`Pin`/`PinOff`) docks the same live view in a side panel of the agent tab (tabs when several are pinned, × to unpin; the conversation shows "pinned to the side panel" with Back here at its card), so it stays in sight while the conversation scrolls and agent updates land in place. A view is drawn in one place at a time, like the expanded view. Pins are kept per conversation in `<data>/gentle-shell-gpui/genui-pins.json` (`{"sessions": {"<session file>": ["id", …]}}`, `genui/store.rs`), restored when the conversation is reopened (`GenUi::restore_pins`, once per session file); pins made before the conversation has a file are saved with it; entries of deleted session files are dropped on the next write.
- **Export** (`genui/share.rs`, files from `gentle_core::genui::export`): the header's `Share2` menu has Copy to clipboard ▸ and Save to file… ▸ (a native save dialog, `prompt_for_new_path`, starting in the project's `docs/` when it exists) for each format, Ask agent to add to docs and Save as template. Formats: diagram → Mermaid (`flowchart LR|TB`, groups as `subgraph`s, node kinds as shapes, edge styles as `-->`/`-.->`/`==>`/`--o`, statuses as `classDef`s, refs as `%%` comments) and SVG (the app's layout); table → Markdown (GFM, aligned, `|` escaped, link cells as links, a Code column for refs) and CSV (RFC 4180 quoting); checklist → Markdown task list; kanban → Markdown (a `###` per column); chart → PNG (an SVG in the theme's colors rasterized at 2× with resvg, `shared/backdrop/preview.rs` `rasterize_at`) and CSV of the data; form → JSON of the values; html → the page; sequence → Mermaid `sequenceDiagram` (actors, `->>`/`-)`/`-->>` by message kind, notes, `alt`/`opt`/`loop`/`par` blocks with `else`/`and`, activation bars); erd → Mermaid `erDiagram` (columns with `PK`/`FK`/`UK`, notes and nullability as comments, crow's-foot ends from the cardinality, refs as `%%` comments); state → Mermaid `stateDiagram-v2` (initial/final as `[*]`, `<<choice>>`, composite groups as nested `state { }`, `event [guard] / action` labels, the current state as a class); timeline → Mermaid `gantt` (sections per group, explicit dates and lengths, `done`/`active` from the progress, the critical path as `crit`, milestones, dependencies as `%%` comments); review → one unified patch (`git apply`-able, every hunk as proposed). Ask agent to add to docs sends `/gentle-ui:event {"op":"docs","id","format","fence","text"}` (`export::docs_command`; the docs format is the kind's first text format, `text` left out over 60 000 bytes); the extension posts a `gentle-ui.event` message (`details: {request: "docs", surface, kind, title, version, format}`, no `id`, so it is no surface version) that starts a turn (steers mid-turn) and answers the outcome with version 0, which no edit being sent waits for. Results show as toasts (`DiagramEvent::Notice`). The app's own todo checklist (Show as checklist) has no Pin or Export tools.
- **Templates** (`gentle_core::genui::template`, `genui/templates.rs`): Save as template writes the surface as the user sees it to `<data>/gentle-shell-gpui/genui-templates/<slug>.json`: `{"format": 1, "name", "kind", "title", "spec", "savedAt"}` (unix seconds; a taken name becomes `Name (2)`…). `/ui-template` (a built-in listed in the `/` menu and the palette as "Insert UI template…") opens the manager over the conversation (insert, rename, delete); `/ui-template <name>` inserts directly. Inserting sends `/gentle-ui:event {"op":"insert","id":<slug>,"version":0,"kind","title","template","spec"}`; the extension normalizes the spec like a `show` (errors answer `ok: false` for that id, shown as a toast), creates the surface (`id` when free, else `ui-<n>`, version 1) and posts a `gentle-ui.event` message whose `details` are the surface plus `inserted: true` and `template`: without starting a turn when idle (the agent reads it with the next prompt), as a steer mid-turn. The app draws the live card at that message (`GenUi::sync` homes inserted surfaces there until a tool call updates them).

### Driving the agent: run plans, subagent boards, live data

Three extensions of the native kinds turn a surface into a control: the user drives the agent from it, and the app keeps it current. The wire stays the same (`gentle_ui` `show`/`update`/`close`, `details`, the `/gentle-ui:event` envelope and the `gentle-ui.outcome` answer); the extension adds what an event asks of the agent to the message it posts (`KindDef.instructions`).

- **Run plan** (`checklist` with `run`): `spec.run` is `true`/`"idle"` (on), `"all"` (the user asked for every pending step) or `"step"` (one step); items carry `status: pending|running|done|failed|skipped` (`status` wins over `done`; only running, failed and skipped are written out, `done` stays). The steps are the items without sub-items; the next one is the first pending. A run is idle again once nothing runs and it is through (`Step`: its step; `All`: no pending step left), in `Checklist::settle` and the extension alike. The header's Run plan tool turns it on (`{op: "run_mode", on}`); Skip on a row is `{op: "status", item, status: "skipped"}` (and back to pending); Run / Run next mark the next pending step running and are sent at once, with any reorder and skips made before, as `{op: "run", mode: "all"|"step", item}`; Stop is `{op: "stop"}`. The event's message then says "Do step 3 next: “…” (id); … report it with gentle_ui update {patch: {items: [{id, status: "done"}]}}" and, for `all`, to go on through the pending steps; the tool summary of a run plan says what is expected now (the running step to report, or the next one to do). Patches take `status` per item (`done` without `status` clears it, and the other way round) and `run`.
- **Subagent board** (`kanban`): a column with `starts: true` dispatches work; a card may say who and what (`agent: {name?, task?}`) and records the subagent (`agentId`, set by the agent). Moving cards into a `starts` column (dragging or Alt-arrows) sends the pending edits at once with one `{op: "dispatch", card, column, agent?}` per card that wasn't in a `starts` column and has no `agentId` (`Board::dispatches`, `kanban::dispatch`); the message asks the agent to dispatch a subagent with its own tool (Desktop RPC has no start method by design) and then `update` the card with `agentId`. The card then follows that subagent from the session's supervision data (`list_subagents`/`agents_update`, or the legacy widget): status, step and cost on the card; its details offer Stop subagent, which emits `DiagramEvent::CancelSubagent` and goes through the same `cancel_subagent` as the agents panel (`SessionView::stop_agent`).
- **Live data** (`table`, `chart`, `checklist`): `spec.live` is `{source, interval?, map?}` (`"jobs"` alone is a shorthand) with `source` one of `jobs` (`list_jobs`/`jobs_update`, else the legacy jobs), `subagents`, `todo` (the `todo` tool's `gentleTodo`), `git:status` (the changed files, `git::snapshot`), `git:log` (the latest 50 commits, `git::history`) or `command` with `command: {cmd (one line, ≤ 500), cwd? (a folder inside the workspace, relative, no ".."), parse: json|lines|csv}`. Interval: none for the pushed sources (jobs, subagents, todo: `SessionView::sync_genui_live` hands them to `GenUi::feed` while a panel shows them), 10 s for git and 30 s for a command by default, clamped to 5–3600 s. `map` picks records and fields with JSONPath-lite paths (`$`, `.key`, `["key"]`, `[0]`, `[*]`/`.*`; without `$` relative to each record): `items` (the records), `id`, `columns: {key: path}` (table; default each column's key), `label`, `status` (read by `live::status_word`: done/completed/passed… done, running/in_progress… running, failed/error/timed out… failed, skipped/cancelled/dropped… skipped), `note` (checklist), `label` + `series: {name: path}` (chart; default each series' name; not scatter). `live::fill` puts the data in the spec (a live table isn't editable; a live checklist is read-only) and the view rebases on it, so the user's selection stays; data waits while an event is being sent and while paused. Records: jobs `{id, label, status: running|done|failed, state}`, subagents `{id, agent, label, status, step, active, model, cost, tokens}`, todo `{title, status, note}`, git:status `{path, status, code, added, removed}`, git:log `{id, hash, short, author, time, subject, files, insertions, deletions}`; a command's `lines` are strings and its `csv` rows objects keyed by the header.
- **Command consent** (`live::Gate`): a command never runs before the user answers the card's question ("Allow this UI to run a command?", the command, its interval and folder): Allow once (this card, until its command changes or the app restarts), Always for this session (every card with this command line and folder in the conversation, `LiveEnv::allowed`), Deny (a strip offers Ask again). A new command from the agent is asked about again. It runs with the user's shell (`$SHELL -c`, `cmd /C` on Windows) in its own process group, with the app's PATH, stdout read up to 1 MiB (more stops it), stopped after 30 s (`pi_rpc::kill_tree`), any exit code accepted when the output parses (test runners exit 1 with a report).
- **When reads happen**: a read source is read when its card is first drawn, then every interval only while the card was drawn since the last 5 s tick in the active window and isn't paused (`LiveState`, `live_tick`); never for a card that is off screen or in a background window. The header shows "Live · updated 5 s ago" (`live::ago`), "waiting for your OK", "not allowed", "paused" or "failed" (the error as tooltip) with Pause/Resume.
- **The agent's todo list**: the Todos island's "Show as checklist" opens the same list as an app-local checklist (`GenUi::show_todo`, id `app:todo`, `live: "todo"`) in place of the conversation, read-only and following the `todo` data; no tool call, no transcript entry, no `/gentle-ui:event`: the extension doesn't know the surface, and the agent changes its todo list with its own `todo` tool (driving steps is what a run plan is for). Ask about this on a row still puts the item in the composer.

### `kind: "review"`: change review before the agent writes

The agent shows a change set it proposes; the user accepts, rejects or comments each hunk; the agent applies only the accepted ones and marks them applied. `GenUi` keeps it as a `Surface::Panel` (`Body::Review`, `features/genui/review.rs`); `gentle_core::genui::review` parses, validates and describes it.

- **Spec**: `{ summary?, files: [{ path, status?: added|modified|deleted|renamed, oldPath?, language?, hunks: [{ id?, header?, oldStart, newStart, lines: [{kind: context|add|del, text} | "+text" | "-text" | " text"], note?, decision?: accepted|rejected, comment?, applied? }] }] }`. Missing hunk ids become `h<n>` (the hunk's place among all hunks, skipping taken ids); a path loses a leading `./` and `\` become `/`; `status` defaults to `renamed` with an `oldPath`, else `modified` (unknown values too); added files start at `-0 +1` and deleted ones at `-1 +0` when no line numbers are given; a line with newlines splits; hunks are sorted by line. Hard errors: no file, a file without path, duplicate paths or hunk ids, a renamed file without `oldPath`, a file without hunks (a pure rename may have none), a hunk without `oldStart`/`newStart`, starting at line 0 with lines on that side, changing nothing, overlapping another, or with context/removed lines in an added file (added/context in a deleted one); at most 50 files, 300 hunks, 1000 lines per hunk, 6000 lines, 1000 characters per line (cut), 300 per path.
- **Text form**: a file may give `before` and/or `after` (whole texts) instead of `hunks`; the extension turns them into hunks (`lineDiff`: common prefix/suffix trimmed, then Myers' O(ND) line diff, a plain replacement past 2000 edits; `diffHunks`: 3 context lines, nearby changes merged). No `before` means added, no `after` deleted. This is the only diff implementation: the agent must read hunk ids and line numbers in the tool result to refer to them, so the extension computes them, and the app only ever receives hunks.
- **Patch**: `applied: [hunk ids]` marks hunks written (final: the card offers no decision on them), `hunks` merge by id (`null` clears a field: `decision: null` asks again; revised `lines` keep the id), `files` upsert by path (replacing the file; the text form works), `remove: { files, hunks }`, `summary`.
- **Decisions** (the event): Send decisions sends the usual `/gentle-ui:event` with `changes` = one `{op: "decide", hunk, decision: "accepted" | "rejected" | null, comment?}` per hunk whose decision or comment changed since the agent's version, and the spec with every hunk's `decision`/`comment`. The extension answers it like any edit and posts a `gentle-ui.event` message whose content says exactly what to do: the accepted hunks to apply as proposed (id, path, `@@` range), the rejected ones not to apply, the comments to address (on an accepted hunk: apply it as the comment asks; on a rejected one: why or what instead; on an undecided one: answer or revise), the hunks still undecided (not to apply yet), the `update` call that marks the accepted ones applied, then the review's summary. Partial sends are fine; later decisions arrive the same way.
- **Blocking variant** (`action: "show" | "update", wait: true`): after validating, the call reports the surface as a partial result (`onUpdate({content, details})`) and waits; Pi forwards it as `tool_execution_update`, `Transcript` keeps a `gentle_ui` call's `partialResult.details` while it runs, and `GenUi::render_tool` draws the live card at a running call that has a surface (a running call without one still says "Drawing…"). `/gentle-ui:event` runs at once even mid-turn, so the user's decisions reach the extension, which ends the waiting call with the same decisions text as its result (and `details` the decided version) instead of posting a message; the outcome widget answers first. The wait also ends, with the review left open and later decisions arriving as messages, when the user presses Stop (the abort signal; Pi keeps a result returned after an abort), after 30 minutes, when the session changes (`session_start`/`session_tree`), or when another `wait` call shows a newer version of the same id. Limits: messages typed while it waits queue as steering behind the call (Stop ends it); a backend restart during the wait loses the pending call (its result was never written), and the agent has to show the review again.
- **Guidelines** teach the flow: before every edit when the user asked for review mode (and, in Proactive mode, before multi-file or risky edits) show a review; write nothing until decisions arrive; apply only accepted hunks (as proposed or as their comments ask), never rejected or undecided ones; then `update` with `{applied: [...]}`; use `wait: true` only when the agent can't continue without the decisions, else end the turn after showing it.
- **Summary** the model reads: files, `+`/`−` totals, "k of n hunks decided", one line per hunk (`[accepted|rejected|undecided|applied] id: path @@ -a,b +c,d @@ header`, its comment), and what to do next.
- **In the app**: the hunks are drawn by the file panes' diff viewer (`gpui_kit` `Diff`/`DiffState`, fed `review::File::patch()`, a Git patch per file; syntax from the path or `language`), with a file list beside it from two files on, a decision bar annotated under each hunk's last shown line (`Hunk::last_shown`), Accept all / Reject all per file (file header) and for the whole review (card header; one undo step each). Keys: j/k move between hunks, a/r accept/reject the current one (the same key again: undecided), c comments (Enter keeps, Esc drops), Shift-A/R decide the current hunk's file, ⌘Z undoes. The footer counts "k of n hunks decided" and sends with Send decisions; the sent row reads "You reviewed …".

### Canvas kinds: sequence, erd, state, timeline

Four more `PanelView` kinds draw on the diagram's canvas (`features/genui/canvas.rs`: dotted grid, pan, ⌘/Ctrl-scroll and pinch zoom, zoom/fit controls, minimap, a details island and a floating rename field) and edit through `genui::edits::Edits` like the other panels, in the same `/gentle-ui:event` envelope. Each is parsed by `gentle_core::genui::<sequence|erd|states|timeline>` with the same defaults and hard errors as the extension's `normalize<Kind>`, which also lays it out (pure, tested).

- **sequence**: `{ participants?: [{id, label?, kind?: actor|service|db|queue|external}] (plain names allowed; when missing, taken from the messages in order), messages: [{id?, from, to, label?, kind?: sync|async|return|self, note?}] (time order; missing ids are m1, m2…; a message to itself is always self), fragments?: [{id?, kind: alt|opt|loop|par, label?, from, to, else?: [{at, label?}]}] (ends are message ids or 1-based numbers), activations?: [{participant, from, to}] }`. Without `activations` each sync call activates its target until the target's next return. At most 30 participants, 300 messages, 50 fragments. Patch: `participants`/`messages`/`fragments` upsert by id (`at`: a message's 1-based place), `remove: {participants, messages, fragments}` (a removed message drops the fragments and activations it bounds), `activations` replaces (`null` derives them). Changes: `add_participant`, `remove_participant`, `order_participants {participants}`, `update_participant` (label, kind), `add_message {message, index}`, `remove_message` (shrinks the fragments and activations it starts or ends), `order_messages {messages}`, `update_message` (label, kind, from, to, note), `set_structure {fragments, activations}`. In the card: drag a header sideways or a message up and down to reorder, drag from one lifeline to another to add a message (named at once), double-click to rename, Alt-arrows move the selection, Delete removes a message; the island sets a participant's or a message's kind.
- **erd**: `{ tables: [{id, name?, columns: [{name, type?, pk?, fk?: "table.column" | {table, column}, nullable?, unique?, note?}] (plain names allowed), note?, ref?: {path, line?, endLine?}, x?, y?}], relations?: [{id?, from: "table.column", to: "table.column", cardinality?: 1-1|1-n|n-1|n-n, label?}] }`. A table id may hold dots (a known table id followed by `.` wins over the last dot); an `fk` without a column points at the target's primary key, else `id`. Every foreign key is drawn: one no relation covers gets its own (`<table>.<column>-><table>.<column>`, `n-1`, or `1-1` when the column is unique or a key). A missing cardinality follows the keys (a foreign key or a pointer at a primary key → `n-1`, from a primary key → `1-n`). `ref` is kept and sent back as is (`"path"`, `"path:42"` and `"path:42-50"` are read too). At most 60 tables, 80 columns each, 200 relations. Patch: `tables` (columns replace) and `relations` upsert by id, `remove: {tables, relations, columns: ["table.column"]}` (what used them goes too). Changes: `move`, `add_table`, `remove_table`, `update_table` (name, note), `add_column`, `remove_column`, `update_column` (name, type, pk, nullable, unique, fk, note; a rename follows into relations and keys), `order_columns`, `add_relation`, `remove_relation` (clears the key it stood for), `update_relation` (cardinality, label). Layout: the layered layout ranks the tables (the "one" side of each relation first) and orders each rank; tables then stack at their own heights; relations leave and enter column rows square to the tables. In the card: drag a header to move a table, drag ● at a column's side to another column to relate them, double-click a name to rename; the island toggles pk/nullable/unique, renames and retypes a column, adds columns and sets a relation's cardinality; Delete removes the selection.
- **state**: `{ direction?: LR|TB, groups?: [{id, label}] (composite states), states: [{id, label?, kind?: initial|normal|final|choice, group?, description?, x?, y?}] (plain names allowed), transitions: [{id?, from, to, event?, guard?, action?}], current?: state id }` (transition ids default to `<from>-><to>`; labels read `event [guard] / action`). At most 150 states, 300 transitions, 30 groups. Patch: `states`/`transitions`/`groups` upsert by id, `remove: {states, transitions, groups}` (a state takes its transitions, a group lets its states go), `current`, `direction`. Changes: `move`, `add_state`, `remove_state`, `update_state` (label, kind, group, description), `add_transition`, `remove_transition`, `update_transition` (event, guard, action), `set_current`. Layout: the diagram's, with initial, final and choice states shrunk to their shapes in the middle of their slot and transitions ending on them. In the card: drag states, drag ● to another state for a transition (its event named at once), double-click to rename a state or relabel a transition; the island sets a state's kind.
- **timeline**: `{ tasks: [{id, label, start: YYYY-MM-DD, end?: YYYY-MM-DD (inclusive) | duration?: days, progress?: 0–1 or percent, group?, dependsOn?: [ids] | id, milestone?}] }` (stored with `start` and `end`; progress as a whole percent; a milestone is one day). Hard errors: bad dates, an end before the start, unknown or self dependencies, dependency loops, more than 200 tasks or 3660 days. Patch: `tasks` upsert by id (`end` or `duration` replaces the other), `remove: {tasks}`. Changes: `set_dates {task, start, end}`, `add_task`, `remove_task`, `update_task` (label, progress, group), `add_dependency {task, on}` (refused when it would loop), `remove_dependency`. `Timeline::critical_path` follows the task finishing last back through the dependency finishing last; `Timeline::late` lists dependencies a task starts before they end (a milestone's day counts as done). In the card: drag a bar to move it and its ends to resize it (whole days; the axis stays put while dragging), drag ● to another task to make it wait, Alt-←/→ moves the selected task a day; the axis shows days, Mondays or months by zoom and today's line comes from the system clock (UTC).
- **Summaries** list participants and numbered messages with fragments; each table's columns with keys and its ref, then the relations; states with kinds and the current one, then transitions; each task's dates, progress, group and dependencies, then the critical path and late tasks. Each kind has a guideline and a small example in `promptGuidelines`.
- **Motion**: only the view's fit and zoom easing (`motion::ViewTween`, as the diagram's), never with reduced motion; drags follow the pointer at once.

### `kind: "html"`: agent-written pages as MCP Apps

For custom interactive visuals (simulations, calculators, prototypes) no native kind fits, the agent writes a page that runs in an isolated web view and speaks the [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) protocol (SEP-1865, `2026-01-26`), so the same HTML works in any MCP Apps host.

- **Spec**: `{ html: string (≤ 512 KiB), height?: px (clamped 120–2000), data?: object, csp?: { connectDomains?, resourceDomains?, frameDomains?, baseUriDomains? } }`. `data` is what the page receives as its tool input and the tool result's `structuredContent`. Origins must be web origins (`https://host[:port][/path]`, `wss://…`, `*.` subdomain wildcards; `http`/`ws` only on `localhost`/`127.0.0.1`; at most 20 per list); anything else (keywords, `*`, schemes, quotes) is an error in the extension (`normalizeHtml`) and in the app (`gentle_core::genui::html`). **Patch**: `html`, `height`, `csp` replace (`null` clears); `data` merges one level (`null` deletes a key). A data-only update reaches an open page as a new `ui/notifications/tool-result`; a new `html` or `csp` reloads it. **Summary**: size, the origins it may reach (or "no network") and the data keys.
- **Security defaults** (`browser::Sandbox`, `genui/html-host.html`, `html::Csp::policy`): the page is served from the app's own scheme (`gentleui://localhost/…`; WebView2: `http://gentleui.localhost/…`) inside a relay document, as an `<iframe sandbox="allow-scripts">` (opaque origin: no same-origin access to the relay or the app, no popups, top navigation, forms, downloads or modals). Its Content-Security-Policy, sent as the response header and as a `<meta>` first in the document: `default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; media-src 'self' data: blob:; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'self'; form-action 'none'`, with the declared origins added to their directives only (MCP Apps host rules). The web view: navigation limited to the app's scheme, `about:` and declared frame origins; `window.open` denied; downloads and device permissions (camera, microphone, geolocation…) denied; ephemeral storage (incognito); devtools only in debug builds. The page reaches the app only through the relay's `window.ipc.postMessage`, and every message is treated as untrusted. The card shows "isolated · no network" or the origins the page may reach.
- **Host protocol** (`gentle_core::genui::apps::Bridge`, pure and tested): `ui/initialize` → `{ protocolVersion: "2026-01-26", hostInfo, hostCapabilities: { openLinks, logging, message: {text}, updateModelContext: {text, structuredContent}, sandbox: {csp} }, hostContext }`; the host context carries `theme`, `styles.variables` (every standard MCP Apps variable, filled from the app's palette and fonts: `apps::style_variables`), `displayMode: "fullscreen"`, `containerDimensions: { width, maxHeight }`, `locale` (from `LC_ALL`/`LANG`), `platform: "desktop"`, `toolInfo` (`gentle_ui`), and changes go out as `ui/notifications/host-context-changed` with the changed keys. Nothing is sent before `ui/notifications/initialized`; then `ui/notifications/tool-input` `{arguments: data}` and `ui/notifications/tool-result`. `ui/message` (role `user`, text blocks; one in flight) becomes `/gentle-ui:event` with change `{op: "message", text}` and is answered once the extension took it. `ui/update-model-context` is answered at once and sent 0.8 s after the last update as change `{op: "context", content, structuredContent?}`. `ui/open-link` (http/https only) replaces the page with a confirmation; Open answers `{}` and opens the link in the in-app browser card (`SessionEvent::OpenWeb`), Cancel answers `-32000 "Link opening denied by user"`. `ui/notifications/size-changed` sets the page's height (up to the room there is). `ui/request-display-mode` answers the current mode; `ping` `{}`; `ui/notifications/request-teardown` collapses the page, and collapsing sends `ui/resource-teardown` and waits up to 0.5 s for the answer. `tools/call`, `tools/list`, `resources/*` and `prompts/list` answer `-32601` (no server behind a `gentle_ui` page; `serverTools`/`serverResources` aren't advertised), unknown requests `-32601`, bad params `-32602`, unparsable JSON `-32700`, a wrong `jsonrpc` `-32600`; unknown notifications are ignored.
- **Extension side**: a `message` event is posted like an edit (`gentle-ui.event`, idle → new turn, busy → steer; version + 1 with the spec unchanged) with the content "From the HTML UI … the user says: <text>" plus any pending context. A `context`-only event starts nothing and is answered `ok` with the current version at once: the extension keeps the latest per page and injects it once, on the next `before_agent_start`, as a hidden custom message (`gentle-ui.context`, `display: false`; MCP Apps: deferred, last update wins).
- **In the app** (`genui/html.rs`): in the conversation an html surface is a compact card (title, version, what it may reach, Open); the live page only runs in the expanded view. A native web view draws above everything GPUI draws and isn't clipped by it, so inside the scrolling conversation it would cover the composer's menus and dialogs and stick out past the list's edges; the expanded view has a fixed place and one web process per conversation at most. The page hides (without waiting for a frame) whenever a screen, a dialog or sheet or the `/` menu is over it, or its tab isn't shown (`Workspace::sync_web_views` → `SessionView::set_web_shown` → `GenUi::set_obscured` → `WebSurface::set_covered`). A message the agent didn't get keeps the page's request open with Retry and Discard in the footer; closing or reloading the page drops it.
- **Esc**: the web view keeps the keyboard, so `HtmlSpec::document` puts a small relay first in the page (`ESCAPE_RELAY`): Esc that the page didn't handle (`preventDefault`) posts `{gentle: "escape"}`, the relay document forwards it like any message, and `HtmlView::receive` collapses the expanded view (`html::is_escape`) before the MCP Apps bridge sees it. Esc with the keyboard anywhere else in the tab collapses it through the session's `Abort`. While any surface is expanded the Todos island is hidden: it floats where the surface's header (and its collapse button) is.
- **Limits**: composer popovers other than the `/` menu (model, effort, attachments chips) open over the page and are hidden under it while open. On Windows WebView2's navigation handler only sees the top document, so a page could navigate its own frame elsewhere (it stays sandboxed and its messages are still untrusted). There is no snapshot of the page in the conversation card.

### On a Gentle Shell server: `gentle_ui` as a host tool

A server session doesn't load the app's extensions, so the app runs `gentle_ui` itself: `gentle_core::genui::host` is the extension's logic in Rust (pure, tested against the extension's behaviour), `features/session/host_genui.rs` wires it to the tab. It is offered (with the other [host tools](#gentle-shell-server-kind-server)) when the server's `capabilities` list `set_host_tools`, `host_message` and `set_host_context`, and Agent UI isn't Off; a tab on this computer, in WSL or through a command keeps the extension unchanged. Methods this client doesn't know in `capabilities` (`set_host_activity`, which only the server calls) are ignored.

- **The tool**: the extension's description and parameters (`host::guide::parameters`; the worked examples, one per kind, sit in the `spec` description), and its rules as the host tool's `guidelines`: the mode's policy first (Proactive or When asked), then the how-to bullets, packed at sentence boundaries into the contract's 16 × 512 characters (`guide::guidelines`). An Agent UI change in Configuration (`/gentle-ui:event {"op":"mode"}`, sent as for a local tab) is answered here: the tools are offered again with the new mode's rules, and Off withdraws `gentle_ui` and sets the Off rule (`OFF_RULE`) as the host context, so the agent knows earlier surfaces are read-only (the extension adds it to the system prompt). A call arriving while Off answers the extension's `OFF_ERROR`.
- **Calls** (`Engine::call`): show, update and close with the extension's ids (`^[a-z0-9][a-z0-9-_]{0,63}$` when free, else `ui-<n>` past every id seen), versions, titles, errors and summaries; a spec or patch sent as a JSON string is read. Each kind's spec is normalized by its own `gentle_core::genui::<kind>` parser and wire JSON (the parsers the app draws with, which mirror the extension's `normalize<Kind>` defaults and hard errors) inside the extension's `invalid <noun> spec:` list (10 errors at most); on top, as the extension does, absolute code refs inside the session's folder become relative and ones outside it are errors, a review file given as `before`/`after` is diffed into hunks (Myers on lines, 3 lines of context, a plain replacement past 2000 differences), and html is checked as `normalizeHtml` checks it. Patches merge per kind as the extension's `patch<Kind>` (`host::patch`). The result is the summary text plus `details` = `{ id, version, kind, title, spec }` (`{ …, spec: null, closed: true }` for close), so the transcript's `gentle_ui` item is drawn exactly as the extension's.
  The rules are the same; the wording of a few errors is the parser's (`"columns" must be an array` where the extension says `spec.columns must be an array`, `ref needs a "path"` for `ref needs a path`).
- **User events**: the surfaces send the same `/gentle-ui:event {json}` commands; `run_extension_command` hands them to `Engine::event` in a server tab instead of prompting. Edits (version check, spec normalized, version + 1), template inserts, docs requests, html page messages and review decisions produce the extension's message text and details, sent as `host_message { customType: "host.gentle-ui.event", display: true, details, deliver: "auto", triggerTurn }` (`triggerTurn: false` for an insert, as the extension's idle delivery); the outcome line the surface waits for (`{ id, version, ok, current | error }`, as the `gentle-ui.outcome` widget carries it) goes to `GenUi::outcome` once the server took the message, then the command reports done. `Transcript` draws `host.gentle-ui.event` messages as `gentle-ui.event` ones, so the event card, inserted templates and rebuilding all follow unchanged. Checklist runs and kanban dispatches add the extension's instructions; with Agent UI Off the event says so (`OFF_NOTE`).
- **Shared context** (html pages' `ui/update-model-context`): kept per page and set as the app's host context (`set_host_context`, provider replaced by the device id), which the server injects as a hidden message before the next run; the tab clears it when that run starts (`agent_start`), so it goes once, as the extension's `gentle-ui.context`. A page message that follows carries the pending context in its text, as the extension's.
- **A review that waits** (`wait: true`): a host tool has no partial result, so the tab gives its running `gentle_ui` item the surface (a local `tool_execution_update`, the same path the extension's `onUpdate` takes) and keeps the call open; the user's decisions answer it with the extension's decisions text instead of a message. A newer waiting call on the same review answers the older one; a cancelled call (`host_tool_cancel`) stops waiting; a session change answers it. While the server takes `host_tool_progress`, the tab's heartbeat keeps the call alive and the review waits without a cap. A server without it fails a host tool call nobody answered after 10 minutes, so there the review gives up after 9 (`host::REVIEW_WAIT`, not the extension's 30); the review stays open and later decisions arrive as messages.
- **State** is the conversation's, as for the extension: `SessionView::sync_view` folds every `gentle_ui` result's and event message's `details` into the engine (a replaced transcript, as after a resume, a reconnect past the server's buffer or a session switch, rebuilds it from scratch; a version older than one the app already has is ignored), so a new device or a restarted app picks up the same surfaces.

### Third-party MCP Apps (not reachable yet)

An MCP server's own UI (a tool with `_meta.ui.resourceUri` pointing at a `ui://` resource) can't be shown: Pi (`@earendil-works/pi-coding-agent` 1.5.2) doesn't advertise the `io.modelcontextprotocol/ui` client extension (`ClientCapabilities` has no `extensions`), drops tool and result `_meta` when it registers MCP tools (`details` is `{ server, tool }`; `structuredContent` isn't persisted), hides `ui://` resources from `list_mcp_resources`, and gives extensions no way to read a resource or call a server's tool outside a model's tool call (`executeTool` exists only inside a registered tool's `execute`). Pi would need: the client capability `extensions: {"io.modelcontextprotocol/ui": {mimeTypes: ["text/html;profile=mcp-app"]}}`; tool `_meta.ui` (`resourceUri`, `visibility`) kept, e.g. in the result `details.mcp = { server, tool, toolMeta, resultMeta }` and in `getAllTools()`; app-only tools (`visibility` without `"model"`) hidden from the model but callable; and an extension API usable outside a turn, e.g. `pi.mcp.readResource(server, uri)` and `pi.mcp.callTool(server, tool, args)` returning the raw MCP results. With those, the extension could attach the resource to the tool result and relay a page's `tools/call` through `/gentle-ui:event`, and the app's host (`apps::Bridge` and the sandbox) would render it.

## Web apps and the in-app browser

`features/browser/` is a general system web view now, not only Gentle Design's canvas. It shows any `http(s)` page in its own floating card; the design canvas, web apps and device cards all live in the same tileable stage list, and the ones an agent opened wait in the instance tray (see Stages and the instance tray).

| Entry point | What happens |
| --- | --- |
| `gentle-open <url>` | A generated shim in `<data dir>/gentle-shell-gpui/toolchain/bin` (`.cmd` on Windows), written at startup by `platform/shims.rs` with `gentle-device`. It runs `<app> --open-url <url>`, which forwards an `OpenRequest` with `url` through the single-instance server to the running window. The agent's shell PATH already contains that `toolchain/bin` via `pi_rpc::child_path()`. |
| `/web <url>` | A composer built-in. It emits `SessionEvent::OpenWeb` without sending a prompt to Gentle Shell; the card shows at once. |
| A shell tool prints a URL | `gentle_core::web::loopback_url` scans the tool's command, result text and extension `notify` messages; only `localhost`, `127.0.0.1` and `[::1]` URLs count (`SessionEvent::AgentWeb`), so a dev server (`Vite`, `Next`, `python -m http.server`, …) appears in the instance tray without asking. Public URLs require the explicit tool. A URL that is already open reuses its card; a new URL adds another one, so the agent can keep a web build and a mobile build visible together. |

Only `http://` and `https://` are accepted by `--open-url` and `/web`. The generated shim is app-owned; no Gentle Shell configuration is modified. The app must be running to forward the request (in the agent context it always is); if it is not, the CLI becomes the primary and opens the window with the page. A canvas `Stopped` notice only closes the card when it is still showing the design, not after it navigated to a web app.

### Agents driving pages (`gentle-browser`, the `browser` tool)

After Tern's `tern browser`: an agent opens a page in a card of its own and drives it while the user watches.

- **Command** (`browser/cli.rs`, ops in `gentle_core::browser`): a `gentle-browser` shim next to `gentle-open` runs `<app> --browser <args>`. `parse_args` turns the arguments (or `--json '<op>'`) into an `Op`; the op goes to the running app as `Message.browser` through the single-instance server, which answers that connection with one JSON line, `{"ok": …}` or `{"error": {kind, message}}`, instead of `ok` (`instance::Incoming::Browser`, a thread per connection, waiting `answer_within(op)`). Exit 1 on an error, 124 on a timeout, 2 on bad arguments. Running it with no app fails; it never starts one.
- **`browser` tool** (`browser/gentle-browser.ts`): written at startup into `<data dir>/gentle-shell-gpui/extensions/` with the app's executable path in it and loaded by every agent (`pi_rpc::set_extensions`). It runs `<app> --browser --json <op>`; a screenshot's PNG comes back as an image block, which the tool card shows (`Item::Tool.images`) and the model sees.
- **Pages** (`workspace/stages.rs`, `browser_request`): `open` creates a named card (`--name`; otherwise its number in `tabs`) driven by the agent, shown unless `--hidden`, or navigates the one with that name. A driven page keeps its native view out of sight (`WebSurface::set_live`; parked at 1280×800 when it never showed), so a hidden page still runs. The header's **Take over** stops the driving (also `release <tab>`).
- **In the page** (`browser/automation.rs`, `automation.js`): each op evaluates the page script (once per document) and starts the operation; the app polls its answer every 100 ms, since a page's promises can't be awaited from outside and an IPC handler would let any page forge answers. `eval` is written into the app's own script (not `eval()`, which a page's CSP may forbid). Snapshots are an outline with refs (`e12`, held in a WeakMap per document); targets also take `text/…`, `aria/[role/]name`, `xpath/…` and CSS. Events are synthesized in the page, not trusted native input: a site that checks `isTrusted` ignores them. An action that navigates away answers `navigated: true` once the next page loaded. `pick` shows an overlay on the page and answers the ref of the element the user clicks (Esc cancels). Screenshots are the web view's own snapshot (`WKWebView takeSnapshot`, WebView2 `CapturePreview`, WebKitGTK `snapshot`), saved as a PNG in the temporary folder.
- **Navigation**: an action counts as leaving when the page fires `beforeunload`, a form `submit` nobody prevented, or the Navigation API's `navigate` (not a hash change) without `navigatesuccess` after it; then it answers `navigated: true` with the next page once loaded. A single-page app that fetches before changing its route answers first and changes after; agents are told to `wait`. `goto`, `back`, `forward` and `reload` mark the document (`window.__gentleMark`) and wait, up to 3 s, for a new one before waiting for it to load; `goto` always loads (`WebSurface::load`), even the address showing. In browser cards, a page's request for a new window (`target="_blank"`, `window.open`) loads in the same card (`WebSurface::follow_popups`, wry's new-window handler); http(s) only.
- **Profiles** (`gentle_core::browser::Profile`, the header's profile button): where a page keeps cookies and storage. Shared is the default store every page used before; Repository (the workspace's folder), Session, Agent (the default for agent-opened pages) and named profiles (New profile…, listed in `settings.json` `browserProfiles`) each get a store of their own: a WebKit data store named by `Profile::store_id` on macOS (14 and later; earlier, the default store), a user data folder `<data dir>/gentle-shell-gpui/browser-profiles/<folder>` on Windows and Linux. Private keeps nothing on disk. Clear website data… clears the page's profile and reloads it. The chooser draws in place of the page, since the native view would cover a menu.

### Agents using desktop apps (`gentle-screen`, the `screen` tool)

The same for native windows. Unlike `gentle-browser`, the command does the work itself (no running app needed): `<app> --screen <args>` (`screen/cli.rs`, ops and rules in `gentle_core::screen`, the OS in `screen/{macos,windows,linux}.rs`).

- **Ops**: `launch [--app NAME] -- <command>` starts the command detached (its own process group) and waits for its first new window (from the process, a child of it, or, when the command hands off like `open -a`, from `--app`); `windows`, `screenshot [--window ID | --app | --pid]` (the whole screen without one), `click`, `type`, `key`, `scroll`, `quit <pid>`. A window's screenshot is scaled to the window's size, so its pixels are the coordinates `click` takes.
- **Who input reaches** (`gentle_core::screen::may_drive`): only processes `launch` started (`<data dir>/gentle-shell-gpui/screen/launched.json`, dead ones dropped) and their descendants; any other window answers `not_allowed` before anything is sent. Capturing has no such rule (it only reads).
- **macOS**: windows from `CGWindowListCopyWindowInfo` (layer 0, points), pictures from `screencapture -x [-o -l<id>]`, input as Quartz events posted at the window's place after `NSRunningApplication.activate` (the pointer moves). Titles and pictures need Screen Recording, input Accessibility (`AXIsProcessTrustedWithOptions`, which shows macOS's prompt); both are asked of the app the agent runs in.
- **Windows**: `EnumWindows` (visible, not cloaked or tool windows; per-monitor DPI aware, physical pixels), `PrintWindow(PW_RENDERFULLCONTENT)` cropped to the DWM frame, `SendInput` after `SetForegroundWindow` (refused when the window doesn't come to the front).
- **Linux (X11)**: `_NET_CLIENT_LIST_STACKING`, `get_image` of the root at the window's place, XTEST input after `_NET_ACTIVE_WINDOW`. Wayland without XWayland answers that it needs X11.

## `/` commands and native screens

Gentle Shell screens are TUI components (`ctx.ui.custom()` returns nothing over RPC). `builtins::classify(text)` decides, in this order:

1. `Submit::Builtin`: Pi built-ins that the app runs over RPC (`BUILTINS`: `compact`, `name`, `copy`, `export`, `reload`).
2. `Submit::Open(Screen)`: `gentle_core::commands::route` (`gentle:usage`, `gentle:stats`, `gentle:agents`, `gentle:jobs`, `gentle:profiles` without arguments, `gentle:commands`, `gentle:changes`). The tab emits `SessionEvent::OpenScreen` and `workspace/overlays.rs` `open_screen` opens the screen.
3. `Submit::Prompt`: sent as is.

`gentle_core::commands::hidden` hides from the `/` menu and the palette the commands that have no effect over RPC (`gentle:customize`, `gentle:guide`, `gentle:voice`, `gentle:music`, `gentle:panel`, `history`) and `gentle-ui:event`, the app's channel to its generative UI extension. The palette applies the same rules in `palette/commands.rs` `command_row`.

Native screens that act on the backend through the shell's own commands: Profiles (`ProfilesEvent::RunCommand`, e.g. `/gentle:profiles publish <name>`), Background subagents on a Shell without `set_background_subagents` (`SettingsEvent::ShellCommand` → `run_extension_command("/gentle:background-subagents enable|disable")`).

## Other integrations

### Provider sign-in (`crates/pi-rpc/src/login.rs`)

Pi has no RPC login command. `LoginHelper::spawn(spec, homes)` writes `login-helper.mjs` (embedded with `include_str!`) to the temp directory as `gentle-shell-gpui-login-<version>.mjs` and runs it with Node: the one from the self-contained or managed install (`spec.bundled`) or `resolve_node`. Arguments: the script and the Pi package (`pi_package`); environment: `PI_CODING_AGENT_DIR=<agent>` and the combined PATH. The helper uses Pi's `ModelRuntime.login` and writes `auth.json` itself.

Its own JSONL protocol: the app sends `list`, `login` (`provider`, `authType: oauth|api_key`), `logout`, `response` (`id`, `value`), `cancel_prompt`, `cancel`; it receives `ready`, `providers`, `prompt` (`text`, `secret`, `select`, `manual_code`), `prompt_dismissed`, `event` (`info`, `auth_url`, `device_code`, `progress`), `done`, `error`. The UI is in `features/providers/`. After a change, the window calls `reload_models` on every tab: a backend only reads credentials at startup.

### Engram (`features/memory/client.rs`)

Blocking HTTP GET (ureq, 8 s, no redirects) on the background executor. Base URL: `ENGRAM_URL`, otherwise `http://127.0.0.1:${ENGRAM_PORT}`, default port `7437`. `ENGRAM_HTTP_TOKEN` adds `Authorization: Bearer`. Routes: `/project/current?cwd=`, `/observations/recent?…&limit=60`, `/search?q=…&limit=40` (with `project=` or `all_projects=true`), and `/observations/{id}` for the memory a session's Engram status opens the screen on when the page doesn't hold it. The `Observation` model, `MemoryTarget`, `status_target`, `encode` and `parse_observations` are in `gentle_core::engram`. The app does not start Engram: Gentle Shell does it with the first session.

For a folder on a Gentle Shell server the same routes go to the server's Engram through a server-level forward (`ForwardedPage`; see Memories under Gentle Shell server), never to this computer's.

### Subscription usage (`features/usage/`)

The preferred path is the Gentle Desktop RPC slice (see "Subscription usage" under RPC protocol). The legacy path below runs only when there is no agent tab, or the backend's `capabilities` are known not to offer `get_subscription_usage` (or answered `unsupported_method`).

`credentials.rs` reads `<agent>/auth.json` and resolves keys the way Pi does (`$VAR`, `!command`); `fetch.rs` makes one GET per card (20 s, no redirects so the token never leaves the origin, `User-Agent: gentle-pi`): Codex at `https://chatgpt.com/backend-api/wham/usage` and NaN at `https://cloud-api.nan.builders/api/usage/quota`. The parsers are `gentle_core::usage::subscription`.

### Gentle Shell and Engram updates (`features/updates/`)

When the active agent tab's backend advertises `get_update_status`, Configuration asks it instead (see Screen reads under RPC protocol; `status.rs` maps the answer); the registry path below runs for every other Shell and when that read fails. "Skip this version" is the app's on both paths.

Same as the launcher's startup check (`lib/gentle-shell-startup-update.ts`): `registry.rs` requests `https://registry.npmjs.org/gentle-pi/latest` (5 s, stable versions only); `cache.rs` stores `startupReleaseCheck` (`checkedAt`, `latest`, valid for one day) and `skippedStartupRelease` in the launcher config, so the terminal and the app agree. One difference: a cached answer that offers nothing is asked again after an hour (`gentle_core::version::cached_answer_holds`), and the fresh answer is written back, so a release published after the last check shows the same day for both. Offline, the day-old answer is used. The offer is decided in `gentle_core::version::offer_for`. `settings/upgrade.rs` performs the install with `gentle-shell upgrade`, then `forget_cached` and `SettingsEvent::BackendUpdated` → `restart_for_update` on every tab.

Engram (`engram.rs`): the installed version from `engram version`, the latest from `Gentleman-Programming/engram`'s latest GitHub release; a "newer" answer holds 6 h, "nothing newer" 1 h; skip in `engram-update.json`. **Update now** (`setup::upgrade_engram`) runs `brew upgrade gentleman-programming/tap/engram` when the running `engram` resolves into a Homebrew `Cellar`, otherwise installs the release binary into `toolchain/bin` (first on the app's PATH). A running Engram server keeps its version until it restarts.

### App update (`features/app_update/`)

`network.rs` queries `https://api.github.com/repos/Gentleman-Programming/gentle-shell-gpui/releases/latest`; `release.rs` (pure) accepts only published `vX.Y.Z` tags, picks the asset with `asset_name` (`gentle-shell-gpui-<v>-macos-<arch>.zip`, `-windows-x86_64.zip`, `-linux-x86_64.tar.gz`) and verifies it against `SHA256SUMS`. `archive.rs` extracts, `install.rs` replaces the binary per OS and `relaunch.rs` reopens the app on exit. 6 h cache and skipped version in `app-update.json`. Dev versions (`is_dev`) are not checked automatically.

### Music (`features/music/`)

gentle-stream's background player (one per user, `gentle-stream daemon`) owns the audio and keeps playing after its clients leave. The app controls it through the same `ctl` CLI gentle-stream itself ships, one short process per request:

- **CLI.** `client.rs` runs `gentle-stream ctl <action> --json` with the resolved player binary (`setup::music::player`), `pi_rpc::command` and `pi_rpc::child_path()` as `PATH`. Actions: `start` (attaches to or starts the player), `status`, `volume 0..100`, `mood <text>`, `toggle`, `next`, `stop`. A successful answer is one machine envelope with `running`, `playing`, `volume` (a whole percent), `name`, `genre` and `mood`; failures are structured (`nothing_playing`, `invalid_request`, `unavailable`). Only `start` may spawn a player; `mood` passes `--gentle-shell <launcher>` so Gentle Shell's model reads the text, and the app starts the player first when nothing is playing.
- **Polling.** Every 4 s while nothing plays (a player started from a terminal shows up), every 1.5 s while one plays, every 1 s while the popover is open. Each poll is one `ctl status --json` process, so a poll never spawns a second player.
- **Quitting.** The app stops a player it started (`ctl stop`); one started elsewhere keeps playing.

The snapshot guarantees no key, mode, bpm or spectrum, so those displays degrade to empty. The player's equalizer is decorative: bars moving on the app's live clock while the snapshot says `playing` (still with reduced motion, low when paused), not levels read from the audio.

### Git (`features/git/`)

`git(cwd, args)` for reads (stderr discarded) and `run(cwd, args)` for side effects, with `GIT_TERMINAL_PROMPT=0` because there is no terminal for credentials. The parsers are in `gentle_core::git`. The session refreshes the snapshot when the turn ends and, at most every 1.5 s, when tools touch files (`refresh_git_soon`).

The Git pane shows each commit author's picture (`features/history/avatars.rs`, rules in `gentle_core::git::avatar`), looked up as Tern does: a GitHub noreply address (`123+login@users.noreply.github.com`) is `https://avatars.githubusercontent.com/u/123`; otherwise, when the main remote (`origin`, else the first) is on GitHub, `GET https://api.github.com/repos/<owner>/<repo>/commits?per_page=1&author=<email>` names the account (`[0].author.avatar_url`), unauthenticated; otherwise Gravatar, `https://www.gravatar.com/avatar/<sha256 of the address>?d=404`. So the address of every author in the loaded commits goes to GitHub's API (for a GitHub repository) and its SHA-256 to Gravatar, once per address: pictures are kept in the data dir's `avatars/` (64 px PNGs) and "no picture" for a week. Four lookups run at once on the background executor, with a 15 s timeout and at most 2 MB per picture. A network failure stops lookups for the session; GitHub's rate limit (403/429, 60 requests an hour without a token) stops only the API, and Gravatar is still asked. Without a picture the row keeps the author's initials.

The activity strip's **GitHub** view (`features/history/contributions.rs`, parsing in `gentle_core::git::activity`) reads the user's contribution calendar, only when that view is picked (again on the pane's reload). The account is `git config github.user`, else a GitHub noreply `user.email`, else the account the commits API above ties to `user.email` in this repository (main remote on GitHub; `origin` when the history isn't read yet), else the GitHub CLI's signed-in account (`gh api user`). The calendar is the profile's public page, `GET https://github.com/users/<login>/contributions` (unauthenticated HTML: each `<td data-date>` day and its `<tool-tip>` count), so private contributions count only when the user's profile shows them. Nothing is stored.

### Browser for Gentle Design (`features/browser/`)

The canvas is detected from the Gentle Desktop `design_canvas` events and seed (see Design canvas under RPC protocol), from the `gentle_design` result (`details.url`, `refreshed`, `stopped`; `opened`/`browserDisabled` are ignored) or from a `notify` "Design canvas: <url>" / "Design canvas refreshed: <url>" / "Design canvas stopped."; only loopback URLs are accepted (`http://127.0.0.1:` or `http://localhost:`). The window shows it in `BrowserPanel`. Implementation per OS: `macos.rs` (WKWebView as a subview), `windows.rs` (WebView2 in its own popup that follows the window), `linux.rs` (WebKitGTK as a child of the X11 window; on Wayland the canvas stays in the browser that Gentle Shell opened, so a Wayland session with pages inside the app never sets `GENTLE_DESIGN_OPEN_BROWSER=0`).

## Limits of an RPC host

- Helpers' model, tokens and cost arrive only from backends whose `capabilities` offer `list_subagents`; the token breakdown is unavailable while a helper is in flight. Older Shells keep the legacy `gentle-agents` widget without model/usage/cost.
- Claude subscription windows arrive through the `rate_limit` event when the backend advertises `get_subscription_usage`; without it the app sees only the legacy limit notices (`notify`), not the full windows.
- Helpers and background jobs stop directly only when the backend offers `cancel_subagent`/`cancel_job`; without them the Agents panel keeps the legacy "ask the agent to run `subagent_cancel`" prompt, and jobs have no cancel.
- Auto mode may reject actions: input over RPC does not count as a live human decision.
- The permission mode of a live session changes over the Gentle Desktop RPC channel when the backend advertises `set_permission_mode`, and its default comes from `get_permission_mode`; a backend without Desktop RPC or that method keeps the legacy path (`permission-mode.json` as the default, save it and restart). See “Permission mode” under RPC protocol.
- Gentle Shell does not play sounds for RPC hosts (`notificationContextAllowed`): `features/alerts/` plays them.
- `ctx.ui.custom()` screens do not arrive: they are rebuilt natively or hidden.
- New credentials are only read when the backend starts.

## How to add an integration

### A new status chip

If the extension already publishes `setStatus` or `setWidget`, it shows up on its own as a generic chip. To give it custom handling:

1. `session/events.rs` `handle_ui`: interpret the key (like `gentle:mode` or `gentle-agents`). The pure interpretation goes in `gentle_core` (like `PermissionMode::from_status` or `activity::parse`) with tests.
2. `session/state.rs`: the new state inside the matching group (`ExtensionUi` or `TurnActivity`).
3. `session/view/activity.rs`: exclude the key from the generic filter and draw the chip with `chip_popover` or `ui::chip`.
4. `session/lifecycle.rs` `start`: clear that state on every start.

If the data comes from an event or a tool result (like jobs), read it in `handle_event` / `TurnActivity`, not in `handle_ui`.

### A native screen for a `/` command

1. `crates/core/src/commands.rs`: a variant in `Screen` and a case in `route`; remove it from `hidden` if it was there. Update the tests (`routed_and_hidden_never_overlap`).
2. `workspace/overlays.rs` `open_screen`: open the screen for the new variant.
3. The screen, in its own `features/<name>/` folder, reading files via `pi_rpc::resolve_homes()`.
4. If it must ask the backend for something, emit an event that the window turns into `run_prompt` or `run_extension_command` (the `ProfilesEvent::RunCommand` and `SettingsEvent::ShellCommand` pattern), or use `send_command` for an RPC command.

The palette and the composer already use `route`/`hidden`; there is no need to touch them. A new Pi built-in goes in `session/builtins.rs` (`BUILTINS`, `Builtin`, `parse_builtin`) and `submit.rs` `run_builtin`.

### A new extension UI method

1. `crates/pi-rpc/src/record.rs`: a variant in `UiMethod` with the protocol field names (`#[serde(rename = …)]`); if it blocks, add it to `is_dialog`. Test in `ui_requests_map_wire_names`.
2. If it is a dialog: rendering and keyboard in `session/view/dialogs.rs`, focus in `events.rs` `prepare_dialog`, answer with an existing `UiAnswer` (add one in `lib.rs` only if the protocol requires it).
3. If it does not block: a case in `events.rs` `handle_ui`.

### A new RPC command

1. A method in `session/rpc.rs` that calls `self.request(json!({"type": …}), cx, |this, result, cx| …)` and uses `report` to show errors.
2. If it changes state read at startup, add it to `refresh_state`.
3. If the backend confirms it with an event, handle it in `handle_event` instead of assuming the result.

### A new Gentle Shell config file

1. Path built from `pi_rpc::resolve_homes()` (`agent` or `config`), never hard-coded paths; consider the project variant (`<cwd>/.pi/gentle-ai/`) if the shell has one.
2. Format and validation in `gentle_core` when they are pure (like `notifications`); reading, caching by `pi_rpc::file_cache::Stamp` and atomic writing in the owning feature.
3. If the shell has a command that changes the file, prefer it over writing the file (the `background.rs` pattern).
4. If the backend only reads it at startup, restart the tabs with `restart_when_idle` or offer `/reload`.
5. Add it to the file table in this document.

### A new HTTP service

Follow `memory/client.rs` and `usage/fetch.rs`: `ureq` with a global timeout, `max_redirects(0)` if there are credentials, `http_status_as_error(false)` and readable errors; always on the background executor; parsers and models in `gentle_core`.

## Checklist

- [ ] Child processes with `pi_rpc::command`; `PATH` = `pi_rpc::child_path()` when they look for user tools.
- [ ] Launcher subcommands with the arguments before `--mode` and the `LaunchSpec` `env`.
- [ ] Gentle Shell paths from `resolve_homes()`; exact schemas and atomic writes.
- [ ] Pure logic (parsers, decisions) in `gentle_core` with tests; IO in `app`.
- [ ] New `UiMethod` variants or keys with a decoding test; state cleared in `start`.
- [ ] Backend restarts with `restart_when_idle`, never in the middle of a turn.
- [ ] Visible RPC errors (`report`) and networking that tolerates being offline.
- [ ] File table and limits in this document kept up to date.
